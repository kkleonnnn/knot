# Loop Protocol v4 提案 —— 从「按时间派角色」改为「按风险分档 + 按证据定独立性」

> **触发**：kk 2026-08-01「现有的守护者/远古守护者之类的评审规则已经不足以支持更远以后的未来了，
> 你参考主流是怎么设立这种评审的」。
> **性质**：**提案，未生效**。v3 仍是现行协议，直到 kk 拍板替换。
> **产物**：§4 是可直接替换进 CLAUDE.md 的成稿；§1-3 是诊断与依据，供你判断值不值得换。
> **写作纪律**：§1 的每条诊断都来自**本条弧的真实事故**，不是理论顾虑；§2 只写**真实存在**的主流机制。

---

## §1 v3 到底哪里不够（逐条 grounded，来自 v0.9 弧实测）

### 1.1 ⭐ 根因：评审者身份**绑定时间**，而不是绑定领域或风险

v3 的 `守护者 = 上一 MINOR 的 Agent`。这个绑定产生四个后果，本弧全部实际发生：

| 后果 | 本弧证据 |
|---|---|
| **知识单调过期** | 守护者多次以「本会话我逐行读过 X」作为依据 —— 那个上下文**只在它自己的会话里活着**，跨会话不可复现。而 v3 要求它对**新**代码做终审 |
| **弧内绑定固化** | v0.9 弧 13 片（v0.9.0~.13）全由同一对执行者/守护者 ⇒ 到 v0.9.13，守护者的 v0.8 知识已隔了 13 片 |
| **产生怪约束** | 「弧中途不能 bump MINOR」正是这个绑定的副产品 —— 它逼出了 2026-08-01 那条 `§MINOR` 规则修订（本弧每片都要重裁一次同一问题） |
| **独立性定义错了** | v3 用「时间距离」代理「独立性」，但真正的独立性是「**不知道实现过程**」。上一 MINOR 的 Agent 恰好知道很多实现过程（同一套代码），却不知道**这一片**的过程 —— 巧合地对，但不是设计出来的 |

### 1.2 Stage 2 已连续两片缺席，而协议**无结构性应对**

v0.9.7 / v0.9.8 两片 Codex 均无额度 ⇒ 每片只能写一遍
「资深因额度的例外决定 · 非 R-LP-v3-EX-1 授权 · 不计其滥用计数 · CHANGELOG 留痕」。

⚠️ **用你自己的规则衡量，这已经过线**：R-LP-v3-EX-3「承诺推迟连续 ≥3 PATCH 未兑现 → 升格红线」
防的正是「**例外反复引用却不升格**」这个形状。两层评审退化成一层，已经是**常态**而不是例外。

### 1.3 远古守护者在 PATCH 内**从未产生价值**

v3 定义它「默认沉睡，仅在整体审核激活」。⇒ 一个角色占着协议篇幅，却不参与日常评审。

### 1.4 例外条款已积累成需人工维护的账本

`R-LP-v3-EX-1` / `EX-2` / `EX-2.1` / `EX-3` / `EX-3-1` + `docs/governance/override-cumulative-log.md`
+ 「计数维度 A」。每条都是「防某个具体滥用」的补丁 ⇒ **治理开销随时间单调增长**。

### 1.5 评审强度与风险**不匹配**

本弧几乎每片都是安全面（跨租户数据出境 / 鉴权拆分 / 凭据 / 审计 / 迁移 / 出网），
但评审强度靠「守护者恰好想到」。**守护者两次自认漏项**：
- 「§4.3 那张表是我在 Stage 3 批准的，漏项那一类我也没枚举到」；
- v0.9.6 「门装错位置错了两次」才收敛到能力处。

⇒ 不是评审者不用心，是**没有结构化枚举**，靠灵感。

### 1.6 ✅ 但有几样**比主流强**，必须原样带走

| 强项 | 证据 |
|---|---|
| **revert-to-bad 取材纪律**（每条「已守护」必须对应一次真跑过的取材） | 本弧靠它抓到 **≥6 次假绿**（`_EVIL_TABLES` 无 `source_id` / `:312` 自己转瞄 / 探针只抛不记 / M5 注入仍绿 / `pytest.raises` 让说明永不显示 / 计数口径逃逸） |
| **grounded 到 `file:line`，「用前必验」** | 本弧多次「实读打败范式推理」（守护者自己数到「第 N 次」：C4 denylist / v0.9.3 死守卫 / v0.9.6 凭据来源 / v0.9.8 `api → repo` 直连） |
| **Stage 1 文档先行 + Stage 4 终稿复核** | 对应主流 design doc + final-diff review，形态已经对 |
| **诚实收窄声称** | 「本片不声称所有平台变更都被审计」「本片只做部分减暴露」—— 守护者点名「这种主动收窄要保持」 |

**⇒ v4 的任务不是推翻 v3，是把 1.1-1.5 换掉、把 1.6 升格成明文原则。**

## §2 主流是怎么做的（只列真实存在的机制 + 它解决 v3 的哪条）

| 机制 | 出处 / 实践者 | 它解决 v3 的 |
|---|---|---|
| **CODEOWNERS + required reviewers** | GitHub / GitLab 原生功能 | **1.1** —— 评审责任按**路径/领域**分派（改 `auth/` 必须 auth owner 批），不按「上一个版本的人」 |
| **Two-person rule / 四眼原则** | 金融、航空、云厂商通行 | 1.2 —— 但它要求**有第二个人**，这正是 KNOT 的稀缺资源（见 §3） |
| **风险分级评审（tiered review by blast radius）** | Google / Meta 内部实践：低风险 1 人 + CI；高风险加**专项 gate** | **1.5** —— 强度跟风险走，不跟人走 |
| **专项 gate：security review / privacy review** | Google、Meta 都有独立的安全/隐私评审队列 | **1.5** —— 安全面不靠「恰好想到」 |
| **Design doc / RFC / KEP / PEP** | Google design doc · Rust RFC · Kubernetes KEP · Python PEP | 已有（= Stage 1），形态对 |
| **ADR（Architecture Decision Record）** | Michael Nygard 提出，广泛采用 | **1.4** —— 轻量、**编号、不可变、带状态**的决策记录，比「在 CLAUDE.md 里改一段」更适合累积治理决策 |
| **Production Readiness Review (PRR)** | Google SRE Book 明载 —— 上线前**清单式**评审，由**独立于开发方**的 SRE 做 | **1.5 + lift** —— 不可逆动作不该是「普通一片」 |
| **Threat modeling（STRIDE 等）** | 微软提出，行业标准 | **1.5** —— **结构化枚举**替代灵感 |
| **Blameless postmortem → action items** | Google SRE / Etsy | 1.6 —— 我们的 §9/§10 实施记录已是这个，但缺「教训 → 检查表」的**制度化回流** |
| **Definition of Done / launch checklist** | 敏捷 + SRE 通行 | 1.6 —— 把 revert-to-bad 从「习惯」升格为「完成的定义」 |

### ⚠️ 主流有一条我们**学不了**

**Two-person rule 靠「人多」换独立性。** KNOT 是**一个人 + 一串会过期的 Agent 上下文**
⇒ 独立性是**结构性稀缺**，加人换不来。

**⇒ 这是 v4 全部设计的出发点：用机制替代人数。**

## §3 ⭐ v4 的核心原则（本提案唯一的新思想）

> ## 评审的产物应当是**哨兵**，不是**意见**。
> 每条评审发现，要么变成**一条 CI / 测 / 清单项**，要么就会随评审者的上下文一起过期。

**为什么这条能替代人数**：意见的有效期 = 评审者上下文的寿命（在 KNOT ≈ 一个会话）；
哨兵的有效期 = 仓库的寿命。**一个人写不出两倍的意见，但能把每条意见固化成不会过期的东西。**

**本弧的实证（两个方向都有）**：
- ✅ v0.9.7 的 6 条 must-fix **全部落成具名测**（M1 三态参数化 / M2 缺键 / M4 内容级 oracle …）
  ⇒ 那些结论现在**不依赖任何人记得**。
- ❌ 守护者三次点名「**散文规则、零守护**」：来源标签「不得进客户端消息」（v0.9.7 §III）·
  `resolve_allowed_hosts` docstring · R-PB2-3 的措辞 ——
  **每一条都是「写下来了但没人守」，而本仓已反复证明这类规则会漂。**

**推论（三条可操作的）**：
1. **T2 以上的评审意见，必须以「哪条测/哪条 CI 会因此转红」结账** —— 否则那条意见不算落地。
2. **反复出现的失效形状，从意见升格为清单**（§4.4 的枚举表就是本弧提炼出来的）。
3. **允许并鼓励「本片不声称 X」** —— 明确的不声称，比含糊的声称更有价值。

## §4 v4 成稿（可直接替换 CLAUDE.md 的 §迭代循环协议）

### 4.1 角色（从 5 个减到 3 个）

| 角色 | 实体 | 职责 | 权限 |
|---|---|---|---|
| **执行者** | 当前工作的 Agent | 测绘 / 出方案 / 写代码 / 跑闸门 / 取材自证 / 提 PR | 读 + 写 |
| **独立评审者** | **任何满足「独立性判据」的一方**（见 4.2） | 按档位做评审，产出**可结账的**意见 | **只读** |
| **资深架构师** | kk | 战略 / 口径 / 不可逆分叉拍板 / 抽查 | 决策 |

**⛔ 废除**：`守护者 = 上一 MINOR 的 Agent` 这个**时间绑定** · `远古守护者`（并入 4.3 的 T3 召集）·
`一个 MINOR = 一个 Agent` 的强绑定（改为「一条**弧**一个执行者」—— 弧由工作内容界定，不由版本号界定）。

### 4.2 ⭐ 独立性判据（替代「时间距离」）

> **一个评审者是独立的，当且仅当它不知道本片的实现过程。**

**可操作形式**：给评审者的输入**只有** ① Stage 1 文档 ② 最终 diff ③ 闸门输出。
**不给**：实现期的探索过程、执行者的自辩、「我试过 A 但不行」这类叙述。

**为什么这个判据比「上一 MINOR」好**：
- 它**不随时间衰减**（上一 MINOR 的知识会过期，「不知道过程」永远成立）；
- 它**可验证**（看给了什么输入，而不是猜某人有多少上下文）；
- 它**不要求特定的人** ⇒ 谁可用就用谁：新起的 Agent 会话 / Codex / kk 本人 / 未来的第二个 AI 源。

⇒ **1.2 的问题结构性消失**：Stage 2「缺席」不再是例外，因为独立评审者不再是某个特定实体。
（现行的 `R-LP-v3-EX-1` 例外条款与逐片留痕**可以废除**。）

### 4.3 档位（评审强度跟风险走）

| 档 | 覆盖面 | 要求 |
|---|---|---|
| **T0** | 文档 / 注释 / 纯测试 / 版本号同步 | 执行者自审 + CI。**无需第二方** |
| **T1** | 普通实现（无下列承重面） | 执行者自审（**含 revert-to-bad**）+ 四闸门 + kk 抽查 |
| **T2** | **承重面**：鉴权 · 租户隔离 · 凭据 / 加密 · 审计 · DB 迁移 · 出网 / egress · 删除数据 · 限流 | T1 全部 **+ 一名独立评审者**（4.2）**+ 强制走 4.4 的枚举表** |
| **T3** | **不可逆 / 放开面**：lift、provisioning、公测门、删数据的运维动作 | T2 全部 **+ PRR 清单评审**（4.5）**+ kk 显式放行** |

**档位由变更面自动决定，不由人判断** —— 建议配一条 CI：diff 命中承重路径清单 ⇒ PR 必须带 `tier: T2+` 标记。

### 4.4 T2 强制枚举表（**本弧提炼，每条都对应一次真实事故**）

> 结构化枚举替代「恰好想到」。每条都要在 Stage 1 或评审里**显式回答**（可以答「不适用」，但不能跳过）。

1. **fail-open 面**：这个变更引入的新判据，写错会 fail-open 还是 fail-closed？
   *（v0.9.7 M1：`is None` vs 真值判断 —— 全片唯一能把 fail-closed 写成 fail-open 的地方）*
2. **oracle 能力**：判据能不能**表示**我要排除的那个事件？
   *（v0.9.5 计数口径逃逸 · 行级 grep 看不见空行 · `error_kind` 分不清是哪道门拦的）*
3. **门的位置**：门装在**能力被行使的那一行**，还是装在决策点？
   *（v0.9.6 错两次才收敛：拓扑 → 决策点 → 能力处）*
4. **消息的位置**：失败说明挂在**真的会失败的那条路径**上吗？
   *（v0.9.6 Stage 4：`pytest.raises(match=)` 让紧随的说明永不显示）*
5. **散文规则**：这次新增的规则里，有哪条**只写在 docstring 而无守护**？
   *（v0.9.7 §III 来源标签 —— 守护者三次点名同一形状）*
6. **声明 vs 生产者**：新声明的东西有生产者吗？新产物有消费者吗？
   *（v0.9.5 E4 零消费者 = 死码 · v0.9.8 只声明有生产者的 Literal）*
7. **顶班**：摘掉一道门时，会不会有**别的门顶班**而让测继续绿？
   *（v0.9.7 摘门：预测 6 红实际 4 红，两条因别的门顶班而绿）*
8. **既有测的绿是真的吗**：有没有测「因为错误的理由而绿」？
   *（`_EVIL_TABLES` 无 `source_id` ⇒ 验的是 ② 不是 ③ · 手工 ctx 不含平台列 ⇒ 永远在验「未配置」）*
9. **契约冲突**：有没有绕开某条契约？**契约冲突常常在说结构错了，不是绕路的对象。**
   *（v0.9.8：分层契约指出的重构，一并溶解了那个 raise/吞的两难）*
10. **策略题的影子**：有没有出现「两个选项都要我定一条策略」？
    *（那往往说明那个失败模式本不该存在 —— v0.9.8 D5）*
11. **诚实收窄**：本片**不声称**什么？（明确写出来）

### 4.5 T3 的 PRR 清单（Production Readiness Review）

- **清单在弧开始时就写好**（本弧已有：CLAUDE.md 的 R-T-GATE 就绪清单）。
- **每项必须指向一条具名测或一条运维步骤** —— 「已评估」不算完成。
- **由独立评审者逐项核**（不是执行者自报）。
- **kk 显式放行**，且放行记录进 ADR。
- ⇒ 这把 lift 从「守护者觉得可以了」变成「**清单全绿 + 逐项有载体**」。

### 4.6 Definition of Done（把 1.6 的强项升格为明文）

一个 PATCH 只有同时满足才算完成：
1. 四闸门全绿（全量 / ruff / import-linter / size；前端动了则 + eslint + vitest）；
2. **每条「已守护」的声称，都有一次真跑过的 revert-to-bad**（并把失败信息贴进记录 ——
   证明它**不只是红，而且红得能看懂**）；
3. T2+ 的枚举表逐条有答；
4. **实施期偏离 Stage 1 的每一处，都在记录里给出理由**；
5. **实施期发现自己写错的东西，写进记录**（本弧证明这是最高价值的一节）。

### 4.7 决策记录改用 ADR（替代「在 CLAUDE.md 里改一段」）

- `docs/governance/adr/NNNN-<slug>.md`，**编号递增、内容不可变**，状态 `proposed / accepted / superseded by NNNN`。
- CLAUDE.md 只留**当前生效**的口径 + 指向 ADR 的链接 ⇒ 治理开销不再随时间单调增长（1.4）。
- 现有的 `R-LP-v3-EX-*` 与 `override-cumulative-log.md` **保留为历史 ADR**，不再新增同类补丁。

| | v3 | v4 |
|---|---|---|

| 评审强度 | 每片同一套三阶段 | **按承重面分 T0-T3** |

## §6 我对采纳方式的建议

1. **v4 不必一次性全换。** 建议先采纳**三条低风险、立刻见效**的：
   - **4.2 独立性判据**（立刻解决 Stage 2 缺席的尴尬）；
   - **4.4 枚举表**（它已经是本弧的经验，写下来即可用）；
   - **4.6 Definition of Done**（把已在做的事写明）。
2. **4.3 档位 + 4.5 PRR** 建议在 **lift 那一片之前**采纳 —— lift 正是第一个 T3。
3. **4.7 ADR** 可以从下一条治理决策开始用，历史不迁移。
4. ⚠️ **我不会擅自替换 CLAUDE.md 的协议段** —— 那是本仓最承重的治理文本。
   你说采纳哪几条、要不要改措辞，我再落。

## §7 自检（还缺什么）

1. **v4 没解决「谁来做独立评审者」的供给问题** —— 它只把「独立」定义得可操作了。
   若长期只有 kk 一人可用，T2 的第二方仍会是瓶颈 ⇒ 那时**唯一的杠杆就是 §3**（把意见变哨兵）。
2. **档位判定需要一份「承重路径清单」** —— 我可以从本弧直接产出（鉴权 / 隔离 / 凭据 / 审计 / 迁移 /
   egress / 限流 的具体文件路径），但那份清单本身会漂 ⇒ 应当**从代码派生**（如从 `.importlinter`
   契约 + 既有哨兵覆盖面反推），而不是手写。**这条我还没想清楚，留待你拍板后再设计。**
3. **4.4 的枚举表会随新事故增长** —— 需要一条纪律：**Stage 4 记录里的新失效形状，必须回流进枚举表**
   （否则它又变成「散文」）。这条我建议写进 4.6 的 Definition of Done。
