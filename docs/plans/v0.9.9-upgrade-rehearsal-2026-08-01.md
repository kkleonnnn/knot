> （升级实操表 / 多副本实测表 / 回滚前置）+ 本记录（证据与诚实边界）。
> **触发**：kk「你可以在本地用 docker 模拟 k8s 环境排练」→「跑」。

## 一、怎么搭的（可复现）

**保真做法**：用 v0.6.1.4 **自己的代码**建旧库，而不是手写 schema —— 因为「按 spec 造的旧库」

```

  → 停旧容器 → 用 knot:v0.9.9 挂同一个数据卷起
```

⭐ 顺带造出一个**真实的脏状态**：上传**部分成功**（表建了、行没写进去，因 F1 的依赖 bug）——
比干净数据更接近真实存量库，于是我手动补了 3 行进去。

## 二、发现（F1–F9）

### ⭐⭐ F1（最重要，且与迁移无关）：回滚不可靠 —— 依赖是浮动的

`requirements.txt`（v0.6.1.4 与今天都一样）**全部 `>=` 不钉版本** ⇒ 今天重建旧 tag 装到的是**今天的依赖**。

**两层含义，第二层是真风险**：
1. 排练的**保真上限**：我建的旧镜像 ≠ 内测服正在跑的那个镜像（后者带部署当时的依赖集）。
2. ⚠️⚠️ **「重建 / 重新部署当前版本」不是一个安全操作**。
   **实证**：v0.6.1.4 的代码 + 今天的 SQLAlchemy 2.0.51 ⇒ **上传功能 500**
   （`List argument must consist only of dictionaries`，v0.8.19 才修）。
   ⇒ 重建旧 tag = 回到一个「**代码旧、依赖新**」的**从未存在过也从未被测过**的组合。

**⇒ 已落 DEPLOY.md**「🔴 回滚前置」：升级前 `docker save` 现网镜像（按 digest 存，别按 tag）；
**backlog：给 `requirements.txt` 钉版本**。

### F2：升级会让所有人重登一次（可预期、不可避免）

v0.6.1.4 签发的 token 载荷实测 `{"sub","exp"}` —— **无 `ver` 无 `tid`**；
v0.9.4 起判别式是「**tid 有无**」⇒ 存量 token 全 401。
**实测**：旧 token → `401 JWT_NO_TID`；重登后 payload = `{"sub":"1","ver":1,"tid":1,…}` 正常。

### F3：该版本 seed 是 `admin/admin123`，且强制改密门是**真的**

未改密时 `/api/admin/*` 一律 **403**（只 `/api/auth/*` 白名单可用）。该版本尚无
`KNOT_INITIAL_ADMIN_PASSWORD`（v0.8.20 才加）。对升级无影响，但**演练/新部署脚本必须先改密**。

### F4：数据根会自己长出备份文件

启动期 audit 自动清理生成 `knot.db.audit-purge-<ts>.bak`（一次启动一个，180KB）。
**升级前测磁盘余量要算上它们**。**升级后已验**：`.bak` 留在数据根不动，**不被当成数据库加载**。

### F5：升级动作本身 —— 干净、快

| 项 | 实测 |
|---|---|
| 停旧版 | 0s |
| 起新版到 `Application startup complete` | **4s** |
| 迁移日志 | `[C4] 存量迁移完成（migrated）：…/knot.db → …/tenants/1/knot.db；旧库备份 …/knot.db.pre-tenancy.bak` |
| uploads | `[uploads-reloc] tenant#1 uploads: skip:fresh`（该版本 uploads 表在主库里，随主库一起迁走 ⇒ 正确） |
| 行数 | `users 3` · `data_sources 2` · `audit_log 8` · `t_reh 3` · `file_uploads 0` —— **逐条相符** |
| 凭据 | 密文前缀**逐字节相同**（迁移不重新加密） |
| `platform.db` | 新建，含 `tenants` + `platform_audit` |
| `platform_audit` | **恰 1 条**：`platform.tenant_create` / `system:boot` / `startup` / `{"db_dir":"tenants/1","seed":true}` |

### F6：我自己在 v0.9.7 写的启动 WARN **在真部署里响了**

tenant#1 的 `allowed_http_hosts` 为 NULL ⇒ 起源租户回退 env + WARN。
**这是设计意图**（三态语义），但它意味着**升级后必须补一步**：显式配该列。
⇒ 已落 DEPLOY.md 升级表下方的「必须补的一步」。

### ⭐⭐ F7：多副本共享卷首启 —— 守护者警告的场景**是真的**，但严重性比预想低

排练刻意选了 `flock` **不互斥**的挂载层（macOS bind-mount）。**先直接验证了这个前提**：
两个容器同时 `LOCK_EX | LOCK_NB` **都成功、等待 0.00s** ⇒ 该层 flock 不提供互斥
（= DEPLOY.md 里「跨节点 RWM/NFS 上 flock 不保证互斥」的最坏形态）。

3 副本同时首启：

| 观察项 | 实测 |
|---|---|
| 结局 | 副本1 `resumed` ✅ · **副本2 exit=1 崩溃** ❌ · 副本3 `skip:migrated` ✅ |
| 崩溃报错 | `sqlite3.OperationalError: disk I/O error`，栈底 `tenancy_migration.py:89` `_backup_db` → `s.backup(d)` |
| 业务数据 | ✅ `integrity_check=ok` + 行数逐条相符 |
| 回滚源备份 | ✅ `.pre-tenancy.bak` 同样 `integrity=ok` + 行数相符 |
| 崩掉的副本重启 | ✅ **一次即自愈** → `skip:migrated` → HTTP 200（K8s 表现 `RESTARTS: 1`，**非** CrashLoopBackOff） |

⇒ **`tenancy_migration` 的容错设计守住了**（不丢数据 / 保住回滚源 / 可续跑 / 自愈）；
**可用性没守住**（一个 pod 崩一次）。且 `disk I/O error` **看起来像磁盘坏了**，会误导值班判断
⇒ DEPLOY.md 已写明「**不要恢复备份、不要回滚，让它重启**」。

### F8：规定顺序**真的能避开** F7

先 1 副本迁完（`migrated`）再扩到 3 副本：**0 traceback**，三副本全 `migrated`/`skip:migrated`，
`platform_audit` **恰 1 条**（seed 与其审计一同幂等 —— 3 个副本不会记出 3 条）。

### ⚠️ F9：一处自我订正 —— 我把严重性说过头了

v0.9.8 设计论证里我写过「多副本共享 PVC 首启并发写 ⇒ `database is locked` ⇒ **崩溃循环**」，
用它论证「同事务审计优于 raise」。**实测**：崩**一次然后自愈、不循环**，报错也**不是** `database is locked`。

- 那条论证的**结论仍成立**（同事务写法的价值在于它根本不需要在 raise 与吞之间选一条策略）；
- 但**支撑论据被我夸大了**。已在 DEPLOY.md 同段落写明，以免被后续引用。

⇒ 教训（与 v3.1-B #2 同族）：**「会发生什么」不能从机制推断出严重性 —— 严重性必须被观测。**

## 三、诚实边界（本排练**验证不到**什么）

1. **🔒 平台迁移链没被真跑到**（守护者提醒过四次，本次**观测坐实**）：从 v0.6.1.4 升级会**全新创建**
   `platform.db` ⇒ 两条平台迁移（`allowed_http_hosts` / `updated_at` 加列）**都是 no-op**
   （实测 tenant#1 行两列均为 NULL 即其证据）。这一面由 v0.9.8 的「构造缺列平台库」单测覆盖。
   **别因为排练全绿就以为平台迁移链被验证过。**
2. **数据是合成的**（阶段一）。真实存量库可能有：更多表、脏行、超大 audit_log、真实上传文件、
   多用户会话。⇒ **阶段二需要 kk 提供内测服真实数据的一份还原副本**。
3. **不是 K8s**。Docker 容器共享 bind-mount ≈ 多 pod 共享 RWM PVC 的**最坏锁形态**，
   但不覆盖：K8s 探针时序 / initContainer / PVC 挂载延迟 / 多节点时钟。
4. **F7 的锁形态是刻意挑最坏的**。单节点本地卷（RWO）上 flock **有效** ⇒ 该场景不会发生。
   即：F7 是「RWM/NFS/跨节点」下的实测，不是「所有多副本部署」的通例。
