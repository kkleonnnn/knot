### ⭐ F6'' 上界阶梯（Q2 裁定 · 可复用规则）

> **上界取「上游自己的版本契约所能支撑的最紧那个」。**

| 实装版本形态 | 上界 | 例 |
|---|---|---|
| `1+`（有 major 承诺） | 下一个 **major** | `requests 2.32.5` → `<3` |
| `0.x`（只有 minor 有意义） | 下一个 **minor** | `fastapi 0.137.2` → `<0.138` |
| `0.0.x`（**任何层级都无承诺**） | 下一个 **patch** | `python-multipart 0.0.32` → `<0.0.33` |

**理由**：0.0.x 在任何层级都没有稳定性承诺 ⇒ **比实测版本更宽的任何声明都是假话**，
而 d3 的目的原文就是「让声明不再撒谎」。

⚠️ **维护成本要正着说**（守护者原话）：对 0.0.x 包，spec 上界**实际等于钉住** ——
**那是正确的，不是负担**，因为精确版本本来就由 lock 钉，**spec 的上界纯粹是一句真话声明**。

### F7' R4 —— 只改一行会直接文件不存在（实测）

`Dockerfile:12` = `COPY requirements.txt .`；`:13` = `RUN pip install -r requirements.txt`
⇒ 把 `:13` 改成读 lock 而不改 `:12`，**lock 根本没被 COPY 进来** ⇒ 构建当场失败。
⚠️ 而**纯负断言（「不得再 install requirements.txt」）连这个都测不出来** ——
删掉整个安装步骤它也通过。⇒ 必须**正向断言**「lock 被 COPY **且**被消费」。

### F8' R10 —— `requires-python` 与实际不符（实测）

`pyproject.toml:9` `requires-python = ">=3.9"`，而 CI **3 处**都是 `python-version: "3.11"`、
镜像是 `FROM python:3.11-slim` ⇒ **3.9/3.10 从未被任何东西验过**。⇒ 收敛到 `>=3.11`。

### ⭐ §2.1 张力已裁（Q1）—— lane 用与 `Dockerfile` 逐字相同的安装命令

**原分歧**：守护者 §II-R3 采纳「lock 当 **constraints** + 安装后集合等值」，而 §III 却把阻断 lane
写成 `pip install --no-deps -r requirements.lock` —— 两处引了 Codex 两个**互斥**备选。
**裁定**：采纳我的解法。**判据**：用不同的安装方式，验的就不是生产路径
⇒ lane 绿而生产可能坏，正是 R8 要防的那类。

#### ⭐⭐ 四层各干一件不同的事，谁都不是冗余（Q1 加层 —— **必须写进 lane 注释**）

| 层 | 它证明什么 | 它**不能**证明什么 |
|---|---|---|
| ① `-c requirements.lock`（constraints） | 装到的版本**不越界** | **不证明闭合** —— constraints 只**限制**版本、**不强制安装**；某个传递依赖若从 lock 里漏了，pip 会**自由解析**它 |
| ② **集合等值**（`pip freeze` == lock） | **闭合**：没有 lock 外的包被拉进来，也没有 lock 内的包缺席 | 不证明它们彼此兼容 |
| ③ `pip check` | 无依赖**冲突** | 不证明代码能用这套版本 |
| ④ **用该环境跑后端全量** | **API 兼容**（R8） | —— |

⭐ **② 是把「constraints」变成「闭合」的那一步** —— 守护者点名：**它最容易被当成冗余省掉**。
⇒ 注释里必须写清四层四职责，否则将来有人会把其中一层当「已被覆盖」删掉
（**本弧反复见过的漂移形态**）。

**为什么 ④ 不可省（Codex R8，守护者称「他最好的一条」）**：
代码若开始用「区间内新版才有的 API」⇒ 浮动 lane **绿**（它装的是新版）· lock 仍满足区间 ·
**只有生产炸**。⇒ 「lock 过期则 d5 会红」**不成立** —— d5 只比版本区间，看不见 API 用法。

#### ⚠️ 两个实施注意（Q1 附带，守护者给）

1. **locked lane 必须是只装生产依赖的干净环境** —— 同环境里**别再** `pip install -e ".[dev]"`；
   集合比对要**排除项目自身**。（本片做法见 §2.3 的步序：比对**先**做，dev 依赖**后**装。）
2. **生产镜像不装项目本体**（`COPY . .` 直接跑）⇒ **镜像内 `pip freeze` 天然干净，与 lane 可比**。
   ✅ **已实测确认**：`Dockerfile` 无任何 `pip install -e .`，`WORKDIR /app` + `COPY . .`
   + `CMD uvicorn knot.main:app`。

### §2.2 阻断 lane 的形态 —— ⭐ 口径按守护者加项 1 **重写**（我原稿过于保守）

`actions/setup-python@3.11` ⇒ **零 Docker Hub 拉取** ⇒ 不把 `continue-on-error` 当初要避的
rate-limit 噪声请回来。

⭐ **正确的口径（守护者订正我）**：`setup-python` 的 3.11 与 `python:3.11-slim` 确非同一个二进制，
但**要紧的不是二进制，是 wheel tag 是否解析成同一批** —— 两者都是 **glibc / x86_64 / cp311
manylinux** ⇒ **选中的 wheel 相同**。
⇒ 本 lane 证明的是「**该版本集合在生产的 wheel 解析画像下闭合，且能过全量**」；
残留差异是**解释器构建本身**，对纯 Python + manylinux wheel **几乎无影响**。

⚠️ **这么写是刻意的**：免得将来有人以「又不是真的一样」为由把这条阻断 lane 降级。
（仍**不**声称「与生产镜像逐字节同构」—— 那只有 docker job 能证，而它 `continue-on-error`。）

### §2.3 阻断 lane 的步序（**顺序本身是承重的**）

```
① pip install（与 Dockerfile 逐字相同的命令）   ← 生产路径
② pip check                                     ← 无冲突
③ 集合等值：pip freeze == requirements.lock      ← 闭合（此刻环境只含生产依赖）
④ pip install -r requirements-dev.txt -c requirements.lock   ← dev 依赖，且不得移动锁定版本
⑤ 断言 lock 内每个包的版本仍**逐条**等于 lock    ← 证明 ④ 没把生产依赖顶上去
⑥ 跑后端全量                                    ← R8：API 兼容
```

⚠️ **③ 必须在 ④ 之前**：dev 依赖会引入 lock 外的包（pytest / ruff …）⇒ 装完再比集合必然不等。
⚠️ **⑤ 不是冗余**：若 `requirements-dev.txt` 的某条约束把 `fastapi` 顶到别的版本，
那么 ⑥ 跑的就**不是 lock 那套** ⇒ R8 的证明作废。`-c requirements.lock` 已在机制上挡住，
**⑤ 是对该机制的验证**（本弧纪律：不要只声称机制生效，要断言它的结果）。
