### §9.4.1 ⭐ 我实施期自捉的三处 oracle 缺陷（**全都是先跑 revert 才发现的**）

1. **Sa2/Sa5 把「抛没抛」当成检查真属性的前置门** —— 原写 `with pytest.raises(...)`，
   摘掉守护后测试停在 `DID NOT RAISE`，而**零写入 / 零备份这两条真正的安全属性根本不执行**
   ⇒ revert 证明不了它们有效（v0.9.6「消息永不显示」的同族）。
   改 `try/except` + **无条件**断言；且 catch `Exception` 而非 `RuntimeError`
   （摘掉 schema 校验后抛的是裸 `sqlite3.OperationalError`，也必须走到零写入那两条）。
   ⭐ **一般化：安全属性是「什么没发生」，不是「抛了异常」。异常只是实现方式之一。**
2. **Sa4 的判据是空的** —— 「同进程连跑 5 次结果相同」：`frozenset` 迭代顺序在**同一进程内是稳定的**
   ⇒ 就算把 `sorted()` 全摘掉也必然相同 ⇒ **判据表示不了要排除的事件**（v3.1-B #2）。
   改为直接断言**有序**（有序才是跨进程确定性的充分条件）。
3. **Sa1 缺「注入前提成立」的前置断言** —— 若 WAL 恰好已被 checkpoint，那行本就在主文件里
   ⇒ copy2 与 backup API **无从区分** ⇒ 本测空跑而全绿。补：先用 copy2 探针证明那行**确实不在主文件里**。

⭐ **「零写入」的 oracle 也换过一次**：不比主文件字节 —— WAL 下主文件可以「没变」而数据已被改写；
而 `PRAGMA wal_checkpoint` 本身重排页 ⇒ checkpoint 后再比字节又**假红**。⇒ 比 `iterdump()`
（完整、WAL-safe、逐字符可比）。**这是「oracle 要能表示你要排除的那个事件」的又一实例。**
