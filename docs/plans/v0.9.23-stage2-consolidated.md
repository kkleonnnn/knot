## §A 执行者自测：一个**文档里没有、也没人要求我查**的缺陷

### A-1 ⭐⭐ 全新库 + N 副本同时启动 ⇒ **2/3 boot 崩**（`database is locked`）

**✅ 实测**（本机、本地文件系统 = RWO 等价，**与 NFS 无关**）：

| 情形 | 结果 |
|---|---|
| 全新数据根 + 3 副本同时 `uvicorn` | ⛔ **启动成功 1 / 3**，两个崩在 `sqlite3.OperationalError: database is locked` |
| 已建好的库 + 3 副本同时启动 | ✅ **3 / 3 正常** |

**崩点**：`platform_migrations.py:102 → tenant_repo.py:49 conn.execute("PRAGMA journal_mode=WAL")`，
经 `main.py:76 tenant_repo.init_platform_db()`（**模块级**，import 即执行）。

**根因（✅ 实读）**：`.c4-migration.lock` 那把 flock 在 `tenancy_migration.py:367` 获取，
而它由 `main.py:82` 调用 —— **晚于** `main.py:76` 的 `init_platform_db()` 与 `:77` 的 `seed_default_tenant()`
⇒ **flock 根本没盖住平台库初始化与租户 seed**。

⚠️ **这订正了 DEPLOY 的框定**：DEPLOY 把并发首启问题归因于「**跨节点** RWM/NFS 上 flock 不互斥」，
读起来像是「同节点有 flock 兜着」。**实测同节点本地盘一样崩**，因为那一段压根不在锁内。

⚠️ **我不声称**：K8s 会不会靠 pod 重启自愈（第一个副本建完库后重启的副本应能起来）——
**我的探针把进程杀了，没有观察到重启恢复**。这条要么实测，要么别写进文档。

### A-2 ⚠️ 这条推翻了我自己 Stage 1 §0.4 的结论

§0.4 我测的是**稳态写**（4 进程 × 200 次短 INSERT，零丢失零错误），
然后把它推广成「**同节点多进程共享 WAL SQLite 是安全的**」。
**启动路径是另一种写模式**（建表 / `PRAGMA journal_mode` 需要排他锁 / 长事务）⇒ 结论不能外推。

⇒ **教训（要入 §9）**：「我测了 X 形态、于是 X 所属的那一类都安全」是**同一个老错的新形态** ——
本仓 CLAUDE.md 已有的形式是「判据要锚在系统真的产出了什么」；
这次的形状是「**我测的是这个负载形态，不是这个组件**」。

## §D 合成发现（**两个 lens 单独都没给出，合起来才成立**）

### ⭐⭐ D-1 A-P1-1 的「降级回进程内桶」会让 B-O5 消失 —— **而那正是危险所在**

- **A-P1-1** 主张：共享库读写失败 ⇒ **降级回进程内 `_Bucket`**（最坏退回 ×N）。
- **B-O5** 指出：4 条既有测**没有平台库** ⇒ fail-closed 会让它们 429。

**把两条放在一起**：采纳 A-P1-1 后，那 4 条测会**静默走降级路径**、**继续通过** ——
⇒ B-O5 那个问题「消失」了，代价是**它们再也没有测到新的共享路径**。
⇒ 整片可能**完全不生效而全套测绿**（v3.1-B #8「测因为错误的理由而绿」的教科书形态）。

**⇒ 必须配的守护（阻断项）**：
1. 一条**断言共享路径真的被走到**的测（例如：计数表里真的出现了该 key 的行 / trace callback 数到了写）；
2. 降级路径**必须计数 + WARN**，且**有一条测断言「正常情况下降级计数 == 0」**
   —— 否则「降级」会从兜底变成常态而无人知道。

### D-2 A-P0-1 与 B-O2 是同一件事的两面

A 说「key 由攻击者构造 ⇒ 恒落库」，B 说「写次数 oracle 对 0 写恒真」。
⇒ **写次数这个判据必须双向有界**：`>= 1`（证明真的走了共享路径，D-1）且 `<= limit`（证明没有写放大，A-P0-1）。
**单向断言在这两个方向上各漏一个真实失效。**

## §G 修订后的合成结论（三个 lens + 自测 合起来才成立的）

### G-1 ⭐⭐ C-6 让 D-1 那个「整片可能inert而全绿」的风险**结构性变小**

D-1 原本担心：A-P1-1 的「降级回进程内桶」会让既有测**静默走降级路径、继续绿**，而共享路径根本没被测到。
**C-6 把本地桶从「降级兜底」升为「正常路径的第一道门」** ⇒ 「有没有走共享路径」不再由**失败**决定，而是由「**本地判定为允许**」决定
⇒ 可以写一条**确定性**的测：本地桶未触顶 ⇒ 共享计数**必须**有该 key 的行。
⚠️ **但 D-1 的守护仍要保留**：降级（库不可用）路径**必须计数 + WARN**，且有一条测断「正常情况下降级计数 == 0」。

### G-2 A-P0-1 与 C-1 是同一个洞的两半 ⇒ **B 项有一个前置条件**

- A-P0-1：key 由攻击者构造（XFF 首段）⇒ 阻断/上界**按 key 生效**的机制统统失效；
- C-1：⇒ 每请求一行新记录，而 DB 侧**没有 `_MAX_KEYS` 的等价物**（实测 4167 写/s、65 B/行）。

⇒ **B 项若不先解决「可信 IP 来源」，最承重的 login 桶上它是装饰品，且顺带把内存 DoS 换成磁盘 DoS。**
⚠️ 而「可信 IP 来源」**不在 kk 锁定的 A+B+C+E 范围内** ⇒ **交 kk 拍**（§H）。

### G-3 我自己在 Stage 1 里的错，已确认 **4 处**

1. ⭐ §0.4「同节点多进程共享 WAL SQLite 是安全的」—— **实测负载形态不能外推**（§A-2）；
2. ⭐ §1-C 的 CAS SQL —— **行不存在时 rowcount=0，purge 永不执行**；且 `app_settings` 是**租户库**表；
3. ⭐ §1-D 把 `upload_engine` 推给 D1 —— **D1 的证据（WAL）对它不适用**（uploads.db 是 rollback-journal）；
4. ⭐ §6 D2「那个数字是 (a) 成立的全部依据」—— **锚在了不承重的桶上**（query 有鉴权、login 没有）。

⇒ 四处**同一形状**：**我把一个在某个前提下成立的结论，用在了那个前提不成立的地方。**
（CLAUDE.md 已有的近亲是「判据要锚在系统真的产出了什么」；本片的新形状是「**我测的是这个负载/这个桶/这个库，不是这一类**」。⇒ 折入 §9。）

## §H ⚠️ 需要 kk 拍的两个范围问题（**我不擅自扩范围**）

### H-1 ⭐ 「可信 IP 来源」要不要进本片？

- **不进**：B 项在 `login`/`change_pwd`（最承重的两个桶）上**是装饰品**，且带来 C-1 的磁盘增长面。
  验收 #4 会**绿着**而爆破防护为零。
- **进**：范围 +1（改 `_client_ip`，加信任跳数配置），但它是 B 成立的**前提**而非附加功能。

**我的推荐 = 进**，理由：这不是「顺手加个加固」，而是「**没有它，B 这一项做完仍然等于没做**」。

### H-2 ⭐ 首启 boot 竞态（§A-1）要不要进本片？

- 事实：全新库 + 3 副本同起 ⇒ **2/3 崩**（实测，本地盘）；已建库则 3/3 正常；
  DEPLOY 已有绕法（「先单副本迁移再扩容」），但它把成因归给「跨节点 flock」⇒ **框窄了**。
- **不进**：至少要**改 DEPLOY 的措辞**（同节点也会崩），否则运维按现有文字会误判。
- **进**：把 `init_platform_db` + `seed_default_tenant` 纳入那把 flock（`main.py:76-77` 移到锁内）。
  ⚠️ 但 C-7 说 `main.py` **headroom = 0** ⇒ 必须同时把逻辑搬进被调模块。

**我的推荐 = 只改 DEPLOY 措辞（必做）+ 把代码修法登记为独立片**，理由：
它**只影响首次部署**，且与 R10' 的主题（稳态多副本安全）**是两件事**；
塞进来会让本片同时动启动序与限流两个承重面。
⚠️ **但「不改 DEPLOY」不是选项** —— 现有文字会让运维以为同节点有 flock 兜着。
