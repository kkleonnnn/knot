## §0 grounded 测绘结论（每条 `file:line`；这些是本片全部设计的事实基座）

### 0.1 ② 「per-tenant `http_spec` 凭据」——**零真实生产者**，本片是**退役一条路径**，不是造机制

| 事实 | 依据 |
|---|---|
| 部署方真实 `_local_catalog.py` 的 2 张 http 表**都用 `source_id`** | 主仓 grounded 读（`source_id: 3`）；env 形态 0 命中 |
| env 形态（`base_url_env` / `auth_header_env` / `auth_value_env`）**只存在于**：注释示例 + TypedDict + executor 实现 + docstring + 测试 | `_template_catalog.py:60-62`（**注释掉的**示例）· `adapters/http/base.py:35-37` · `executor.py:90-128` · `tests/services/test_http_planner.py:21,33-35,241-242` · `tests/test_no_env_value_in_messages.py:202-205` |
| `source_id` 路径的凭据**已经是 per-tenant 机制** | `http_planner.resolve_spec:445-452` → `get_datasource` → `get_conn`（租户库 + Fernet） |
| ⇒ ② 的实质 = **删掉 env 模式**，让「凭据来自进程 env」这件事**结构上不可表达** | —— |

**推论（Stage 2/3 请重点核）**：② **不需要**新机制。「per-tenant 凭据」这个能力**今天就有**，
缺的是**把绕过它的那条路封死**。这与我进 Stage 1 前的预判一致，但与 R-T-GATE 清单的措辞
（「per-tenant `http_spec` 凭据」听起来像要**造**）不同 ⇒ §9 更新清单措辞。

### 0.2 ③ 真缺口 = allowlist 是**进程级共享**（不是「没有 allowlist」）

| 事实 | 依据 |
|---|---|
| allowlist 唯一来源 = 进程 env `KNOT_HTTP_ALLOWED_HOSTS` | `url_allowlist.py:30` |
| 生产调用点**恰 3 处** | 读侧 `executor.py:133`（能力处）· 写侧 `admin/datasources.py:31`（存前）· 探测 `admin/datasources.py:66`（HEAD probe 前） |
| 未设 env ⇒ 空集 ⇒ 全拒绝（secure by default） | `url_allowlist.py:31-33` |
| ⇒ 缺口：**每个租户都继承部署方内网 API 主机的可达权** | 即 `url_allowlist` docstring 自己写的威胁模型「防 admin UI 用户配置任意 endpoint 攻击内网」，在多租户下**按租户失效** |

**② 关闭后 ③ 仍是真缺口（别以为 ② 顺手带走它）**：② 关闭后 base_url 只能来自租户**自己的**
数据源行，凭据也是自己的 ⇒ **没有凭据泄漏**。但租户 #2 的 admin 仍可把部署方的真实 API 主机
填进自己的数据源，用自己的 token 去打 —— 拿不到数据，但**探测 / 打内网** 这件事成立
（若该 API 有任何免鉴权端点则直接暴露）。⇒ ③ 独立成立。

### 0.5 ⭐ 架构死结与解（本片最需要被对抗的一条）

**死结**：
- OOS-1v2 要求**租户归属列只在平台库** ⇒ per-tenant allowlist 的载体必须在 `platform.db`；
- 门必须装在**能力处** = `execute`（v0.9.6 守护者四轮统一诊断：「门装在能力被行使的那一行」）
  ⇒ 读 allowlist 的代码在 `knot/adapters/`；
- `.importlinter` 契约 `adapters-no-business` **禁** `knot.adapters` → `knot.api|services|repositories`
  ⇒ **`execute` 不能直接读平台库**。

**解 = 用既有接缝，不发明新模式**：
- `tenant_repo.get_tenant` 用 **`SELECT *`**（`tenant_repo.py:77`）⇒ **给 `tenants` 加一列，
  它自动出现在 tenant ctx 里**（ctx **就是**租户行 —— `tenant_context.py:45` `set(tenant_row)`）；
- `adapters` 读 `knot.core.tenant_context` **已有先例且已过审**（v0.9.6 的 owner 门就在
  `executor.py` 里 import `is_owner_tenant`；`core` 不在 `adapters-no-business` 的禁列）；
- ⇒ **零分层例外、零新模式、零 hook registry、零启动期 wiring**。

**并且这条路线 v0.9.5 已经预先挡住了它的泄漏面**：`tenant_repo._PUBLIC_COLS`（`:51-53`）的注释原文
「若将来给 tenants 加列…`SELECT *` 会**自动**把新列吐进 HTTP 响应。**这是已登记的路线，不是假设风险**」
⇒ 平台只读端点走**显式投影**，新列不会被 `GET /api/platform/tenants` 吐出。

**ctx 形状可行性**：全仓对 ctx 字典**无 keys/形状断言**（实测：`current_tenant()[...]` 全是取
`["id"]`；`test_platform_admin.py:299` / `test_bi_share.py:100` 的 keys 断言是**别的 DTO**）。

### 0.6 `platform.db` **无迁移机制** ⇒ 本片加**第一条平台迁移**（照既成范式）

- 平台 schema 只有 `CREATE TABLE IF NOT EXISTS`（`platform_schema.sql:11`），
  `init_platform_db` 只 `executescript`（`tenant_repo.py:38-43`）⇒ **加列对存量 `platform.db` 无效**。
- 租户库**有**完整 additive 迁移范式：`repositories/migrations.py` —— 幂等
  `PRAGMA table_info(...)` → `ALTER TABLE ... ADD COLUMN`，带日期/版本注释（18 处先例）。
- ⇒ 本片照该范式加 `_run_platform_migrations(conn)`，由 `init_platform_db` 在 `executescript` 后调用。

### 0.7 `slug` **无格式校验** ⇒ 否决「env 名派生」备选（见 §7）

`tenant_repo.py` 对 `slug` 零格式校验（仅 DB `NOT NULL UNIQUE`）。若用
`KNOT_HTTP_ALLOWED_HOSTS__<slug>` 这类 env 名派生，两个不同 slug 可**塌进同一个 env 名**
（`acme-co` / `acme.co` → `ACME_CO`）⇒ **跨租户放宽 = fail-open**。列按 `tenant id` 键，结构上无此问题。

## §1 决议（D1~D10）

### D1 ② = **强制 `source_id`**，退役 env 模式**与**直填模式

`http_spec` 的两条「自带凭据」路径全部退役，`execute` 的凭据解析只剩一条：
- **删** `executor.py:90-128` 的 env 模式（`base_url_env` / `auth_header_env` / `auth_value_env`）；
- **删** `adapters/http/base.py:35-37` 的三个 TypedDict 字段；
- **删** `_template_catalog.py:60-62` 的注释示例（否则示例教人走已退役的路）；
- `resolve_spec` 保持**无条件从 datasource 行取** `base_url` / `auth_header` / `auth_value`
  （今天的实际行为，§0.3-1），并**新增**：spec 无 `source_id`（或该 source 不是 http 型）⇒
  `pick_http_route` 返 `None`（软降级落 SQL，与 v0.9.6 Layer 0 同形），**且** `execute` 侧
  `base_url` 空 ⇒ `HTTPAuthError`（硬边界；不依赖上游是否降级）。

> **为什么直填也退役**：直填的 `base_url` 由 `PUT /api/admin/catalog`（零校验）写入 ⇒
> 绕过 `datasources.py:150,194` 的写侧 allowlist 门。留着它，③ 的写侧守护就有一条旁路。
> **注意这不是「多做一件事」**：③ 的正确性依赖「base_url 只能来自过了写侧门的数据源行」。

### D2 ③ = `tenants.allowed_http_hosts` 列（TEXT，逗号分隔），**per-tenant 替换，永不取并集**

```sql
ALTER TABLE tenants ADD COLUMN allowed_http_hosts TEXT;   -- NULL = 未配置；'' = 显式全拒绝
```

解析规则（在 `url_allowlist.get_allowed_hosts()` 内，**能力处不变**）：

| 租户 | 列值 | 解析结果 |
|---|---|---|
| 任意 | 非空字符串 | **该列的 host 集**（**不**与 env 取交集或并集） |
| 非 owner | NULL 或 `''` | **空集 = 全拒绝**（fail-closed） |
| owner（`OWNER_TENANT_ID`） | NULL（未迁移） | **回退 env `KNOT_HTTP_ALLOWED_HOSTS`** + **启动期 WARN** 一次（D3） |
| owner | `''`（显式空） | 空集 = 全拒绝（部署方明确表达「禁」，**不**回退 env） |

**为什么替换而非交集**：若与 env 取交集，部署方为了让租户 #2 能访问 host X，必须把 X 也写进
env —— 而 env 是 **owner 租户的** allowlist ⇒ **给客租户开权会同时放宽 owner 的可达面**。交集在这里
是**反向的**。⇒ 每个租户一份，**永不取并集**（这条要有哨兵）。

**NULL vs `''` 的区分只对 owner 有意义**，但两状态语义清晰（「未配置」vs「配置为空」），保留。

### D3 owner 回退 env + **启动期 WARN**（单一去向的迁移路径，不制造漂移）

- owner 列为 NULL 时回退 env ⇒ **现网行为逐字不变**（内测服的 ConfigMap 不动即可继续工作）；
- 启动期 WARN 一次（照 v0.9.6 D8 `warn_if_owner_tenant_not_served` 的既成形状）：
  提示「owner 租户仍在用 env allowlist，请迁移到 `tenants.allowed_http_hosts`」；
- **不做启动期自动 seed**（把 env 值写进列）：那会制造**漂移** —— 运维改 ConfigMap 重启后列不跟随，
  形成「改了没反应」的静默 no-op。回退 + WARN 让 env 在迁移完成前**保持权威**。
- ⚠️ **WARN 只报 env 名，绝不报 env 值**（#262；v0.9.5 must-fix 同款）。

### D4 解析点 = `url_allowlist.get_allowed_hosts()`（三个生产调用点**零改动**自动跟随）

`is_url_allowed` / `check_url_allowed` 签名不变 ⇒ `executor.py:133`（读侧）+
`datasources.py:31,66`（写侧 + 探测）**自动**变成 per-tenant，**无需逐点改**。
这是本片最重要的实现杠杆：**一个 choke point，三个调用点全覆盖**。

⚠️ **契约变化必须写明**：`get_allowed_hosts()` 从「永不抛」变成「**无 tenant ctx 时抛
`TenantContextError`**」（`current_tenant()` 的既有行为）。
- 与仓内 fail-closed 纪律一致（`get_conn` 同形）；
- 两个生产调用点都在请求路径内（ctx 必有）；scheduler tick 走 `resolve_single_tenant` 建 ctx；
- **刻意不 catch**：v0.9.4 MF3 的教训是「fail-soft 吞掉 `TenantContextError` = 安全信号静默丢失」。
  这里吞掉虽是 fail-**closed**（空集 = 拒绝），但会**掩盖 ctx 缺失这个事实**；让它响。
- ⇒ 无 ctx 的既有测**按设计会红**（§4.3）。

### D5 摘掉 v0.9.6 的 owner 门（**最后一个 commit**）

v0.9.6 在 `executor.execute` 开头的 `is_owner_tenant()` 硬边界，其注释明写
「**只有 ②③ 都落地才可移除本门**…别单独摘」——本片正是那个时刻。
- 摘门放**序列最后**一个 commit ⇒ **前面每个 commit 的安全性单调不降**；
- 摘门**在生产上不可观测**：R-T-GATE 仍硬锁第二 active 租户（`assert_no_second_active_tenant_served`）
  ⇒ 现网仍只有 owner 被服务；
- 但**测试上可观测**：复用 v0.9.6 的 `non_owner_client` fixture 形状（owner suspended + 非 owner active）
  ⇒ ②③ 的机制**有真实端到端覆盖**，不是「correct-but-untested」。
- ⚠️ **不留「改谓词」的折中**（如把门改成「有没有配 allowlist」）：那会与 D2 的解析规则重复表达同一件事。

### D6 写侧/探测侧同步（D4 的自动结果，但需**各自的测**）

## §4 验收

### 4.1 must（逐条须有具名测 + 取材证明）

## §7 被否决的备选（**请 Stage 2/3 重点攻这一节** —— §0.5 是本片唯一的架构决策）

| 备选 | 否决理由 |
|---|---|
| **A. env 名派生**（`KNOT_HTTP_ALLOWED_HOSTS__<slug>`） | `slug` **零格式校验**（§0.7）⇒ 两 slug 可塌进同一 env 名 ⇒ **跨租户放宽 = fail-open**。且需重启才能给新租户开权。 |
| **B. 独立表** `tenant_allowed_hosts(tenant_id, host)`（更规范化） | 能力层（`adapters`）要读它必须 import `repositories` ⇒ **破 `adapters-no-business`**。除非加分层例外或 hook port（见 C/D）。**唯一优势**是多值规范化，而逗号分隔 TEXT 与既有 `KNOT_HTTP_ALLOWED_HOSTS` 格式**一致**（同一解析函数）。 |
| **C. resolver port / hook registry**（`url_allowlist` 声明 Protocol，启动期由 app 注入） | 仓内 `adapters` 的既有范式是 `typing.Protocol`（**形状**契约），**无**「上层运行期注入 callable」先例 ⇒ 这是**新模式**。且引入「注入前 / 注入后」两个状态 = 新的 fail-open 面（忘了 wire ⇒ 默认值决定安全性）。 |
