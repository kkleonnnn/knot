### 0.2 ⭐ 引擎缓存：真实陈旧面比文档窄，但**有一处比文档说的严重**

三个缓存点的键（`engine_cache.py` 实读）：

| 站点 | 缓存键 | 键里**有**的连接参数 | 键里**没有**的 |
|---|---|---|---|
| `get_user_engine` 多源（:177-183） | `(tid, uid, "{host}:{port}:{user}")` | host · port · user | **password · database** |
| `get_user_engine` legacy（:266-268） | 同上 | 同上 | 同上 |
| ⭐ `get_engine_for_source`（:303-306） | `(tid, "source", source_id)` | **无** | ⭐ **全部** |

⇒ **两处订正**：
1. **改 host / port / user 是当场生效的**（键变了 ⇒ 必然 miss）—— 文档说的「1 小时用旧连接」对这三项**不成立**；
2. ⭐ **但 `get_engine_for_source` 的键里零连接参数** ⇒ 该站点**所有字段**（含密码）都陈旧最多 1 小时
   —— 文档把三个站点当成一个说，**恰好把最严重的那个说轻了**。

⇒ **真实陈旧面 = ①②站点的 `db_password` / `db_database` + ③站点的全部**。
- `db_password` 陈旧 ⇒ 轮换密码后别的副本**继续用旧密码建新连接** ⇒ 认证失败（用户可见）**或**旧密码仍有效（**安全**：撤销无效）；
- `db_database` 陈旧 ⇒ 别的副本查**旧的库清单** ⇒ **数据范围错**（比连接失败更隐蔽）。

⚠️ **另外两条把文档的处方否掉了**：
- ⭐ **`data_sources` 表根本没有 `updated_at` 列**（`schema.sql:91-108` 实读，只有 `created_at`）
  ⇒ 「比对 `updated_at`」**按字面实现不了**；加列 = 加一条「每个写路径都要记得维护」的约束
  = 本仓反复被烧的那种漂移源。
- ⭐ **「**而非**靠 TTL」是错的** —— 缓存条目里还存着 `schema`（**远端库的表结构**，
  可以在数据源行完全不变的情况下变化）⇒ **TTL 是在管 schema 陈旧，指纹管连接参数**，
  **两者都要，不是二选一**。

### 0.3 限流：6 个桶，三类性质（`_rate_limit.py:32-44` 实读）

| kind | 限额 | 键 | 性质 | ×N 后果 |
|---|---|---|---|---|
| `login` | 10 / 60s | IP（**跨租户全局**） | 爆破防护 | 有效限额 ×N |
| `change_pwd` | 5 / 60s | IP | 爆破防护 | ×N |
| ⭐ `totp_verify` | 5 / 60s | `{tid}:{kind}:{uid}` | **第二因子爆破防护** | ×N（**最承重** —— 6 位码空间 10⁶，限额直接决定可猜次数） |
| `totp_enroll` | 3 / 3600s | tid:uid | 防 secret 生成滥用 | ×N |
| `totp_enroll_complete` | 10 / 3600s | tid:uid | **封顶 bcrypt CPU** | ×N |
| `query` | 30 / 60s | tid:uid | **成本**（LLM burn） | ×N |

⚠️⚠️ **锁定文档说「共享计数器写平台库可接受」漏了一件事**：
**限流器要防的那种流量，恰恰是会把共享计数器打爆的流量。**
攻击者每秒 1000 次登录尝试 ⇒ 每次都读写平台库 ⇒ **限流器变成对 SQLite 的 DoS 放大器**。
⇒ 设计必须让「**已超限**」这个状态可以**本地判定**（见 §1-B）。

### 0.4 ⭐⭐ 存储层：本片最根本的一行，而它不在任何表里

- 连接形态：`sqlite3.connect(path, check_same_thread=False)` + `PRAGMA journal_mode=WAL`
  （`base.py:80-82`；平台库 `tenant_repo.py:47` 同形）。**无显式 `timeout=`** ⇒ 走 Python 默认 **5.0s** busy timeout。
  全仓**无 `database is locked` 重试逻辑**（`repositories/` grep = 0 处）。
- ✅ **实测（本机，4 进程 × 200 写同一 WAL 库，逐字照抄 `get_conn` 形态）**：
  `期望 800 / 实际 800 / 零丢失 / 零错误 / 最慢 0.16s` ⇒ **同节点多进程共享 WAL SQLite 是安全的**。
- ⚠️ **跨节点未验、且有已知上游限制**：SQLite 的 WAL 依赖 `-shm` 共享内存映射，
  **官方文档明示不支持跨主机的网络文件系统**（此条为**转述上游约束，非本机实测** —— 沙箱内无 NFS 可测）。
  本仓已有旁证：`DEPLOY.md:473`「跨节点共享卷（K8s RWM/NFS PVC）上的 `flock` **不保证跨节点互斥**」
  + `platform_audit_repo.py:28`「多副本 + 共享 PVC 首启并发写 `platform.db` ⇒ `database is locked` ⇒ **全副本 boot 崩循环**」。

⇒ ⭐ **这是 §6 D1 的由来**：若 PVC 是 **RWX/NFS**，那么**修进程内缓存是修错了地方** ——
存储层就不成立，多副本在任何写路径上都不安全。若是 **RWO（多副本被迫同节点）**，
则实测已证明存储层没问题，R10' 的作业面就正好是本文档 §1 那几项。

### 0.5 ✅ 实测：为什么共享计数器**必须**是单条原子 SQL

4 进程 × 150 次并发自增同一行（同一份 WAL 库）：

| 写法 | 期望 | 实际 | 丢失 |
|---|---|---|---|
| **先 `SELECT n` 再 `UPDATE SET n=?`**（= 限流器「读计数→判断→写回」的形状） | 600 | **155** | ⛔ **445（74%）** |
| **单条 `UPDATE SET n=n+1`**（= 调度器 `claim` 的形状） | 600 | 600 | ✅ **0** |

⇒ 「共享计数器」若写成读-判断-写回，**在 4 副本下会漏掉 74% 的计数** ——
限流器会以为没人来过。**这不是理论推演，是上面那张表的实测数字。**

<details><summary>两条实测的可复跑形态（Stage 1 = 0 代码，故不落文件；实施期它们变成 §3 #4/#6 的测）</summary>

```python
# ① 存储层：N 个独立进程并发写同一 WAL 库（逐字照抄 base.get_conn 形态：无显式 timeout）
#    每次都 sqlite3.connect(...) → PRAGMA journal_mode=WAL → INSERT → commit → close
#    4 进程 × 200 次 ⇒ 期望 800 / 实际 800 / 错误 0

# ② 丢更新：同一份 WAL 库，4 进程 × 150 次自增同一行，两种写法对照
#    read_then_write: SELECT n → UPDATE SET n=?      ⇒ 600 期望 / 155 实际 / 丢 74%
#    atomic:          UPDATE SET n=n+1               ⇒ 600 期望 / 600 实际 / 丢 0
```

⚠️ **必须是真子进程，不能用线程** —— 线程共享模块级状态，
「每副本一份」这个事实在线程里**表示不出来**（六问②）。

## §1 修法

### R10'-A ⭐ 引擎缓存：**连接指纹进缓存键**（+ 保留 TTL 管 schema）

**做什么**：三个站点的缓存键各追加一段 `fp` = 「**真正用来建这个 engine 的连接参数**」的 sha256 前缀
（`db_type|host|port|user|password|database`）。任一参数变 ⇒ 键变 ⇒ **必然 miss ⇒ 重建**。

**为什么这么修（而不是文档写的 `updated_at`）**：
1. **零 schema 变更**（`data_sources` 没有 `updated_at`，加列 = 加一条「记得维护」的约束）；
2. ⭐ **三个站点都在查缓存之前就已经把权威行读出来了**（实读：site 1 `get_user_source_ids`+`get_datasource`
   循环 · site 2 caller 传进来的 `user` 行 · site 3 `get_datasource(source_id)`）
   ⇒ **指纹是零额外 DB 读**；TTL 省的从来就不是那次读，是 `create_engine`+`test_connection`+`get_schema`；
3. ⭐ **符合本仓的修法优先级**：让「门看到的」与「真正被用的」**结构上不可能不同**，
   优于「改的时候记得去失效」（`invalidate_*` 今天只有 3 个调用点，且**只对本副本生效**）。

**保留什么**：`_TTL_SEC = 3600` **不动** —— 它管的是**远端库 schema 陈旧**（行不变也会变）。
⇒ 两个机制**正交**：指纹管「配置变了」，TTL 管「远端变了」。

⚠️ **指纹只存摘要，不存明文**；且**不得进日志 / 异常**（#262 同族）。

### R10'-B ⭐ 限流：按性质分两档 + **本地阻断缓存**

**共同形状（照调度器 `claim`）**：计数走**单条原子 SQL**，绝不 read-then-write（§0.5 实测 74% 丢失）。

- **安全档**（`login` / `change_pwd` / `totp_verify` / `totp_enroll` / `totp_enroll_complete`）：
  计数落**平台库**（`login`/`change_pwd` 是 IP 键、**跨租户全局** ⇒ 本就该在平台库）。
  ⭐ **本地阻断缓存**：一旦某 key 在本窗口内被判超限，本副本把「阻断到 T」记在内存里，
  **该窗口内后续请求直接本地拒、不再碰库** ⇒ 每 key 每窗口的库写次数 **≤ limit**（login 即 ≤10）
  ⇒ **攻击流量不放大成 DB 写**（这正是 §0.3 那条被漏掉的约束）。
  ⚠️ 阻断缓存**只能让判定更严，不能更松** —— 它只缓存「拒绝」，从不缓存「允许」。
- **成本档**（`query`）：**待 kk 裁定**（§6 D2）—— 三条路各有代价，我给推荐但不擅自定。

### R10'-C 启动期 audit auto-purge：改**原子认领**

今天 `main.py:293-300` 是 read-then-write（读 `audit.last_purge_at` → 判 7 天 → 跑 → 写回）
⇒ N 副本同时启动 ⇒ 同时判「该跑」⇒ N 个并发 chunk DELETE。
⇒ 改成**条件 UPDATE 认领**（`UPDATE app_settings SET value=? WHERE key='audit.last_purge_at' AND (value IS NULL OR value < ?)`，
按 rowcount 决定跑不跑）—— **与调度器 `claim` 逐字同形**，不自创第二套写法。

### R10'-D `upload_engine`：**评估结论 = 不动**（诚实记，而不是顺手改）

`_upload_engines` 每副本一份、无 TTL，但它缓存的是**到本租户 `uploads.db` 的 SQLAlchemy engine**
⇒ 键 `(tid, 绝对路径)`，路径由 ctx 派生、**不含任何会变的配置** ⇒ **不存在陈旧语义**。
多副本并发写同一份 `uploads.db` = §0.4 那条存储层问题的实例，**由 D1 统一决定**，不是本项自己的问题。
⇒ **本片不动它**；但**必须写进 DEPLOY 那张表**（它今天不在表里 = 下一个人重扫时还会漏）。

### R10'-E 哨兵：让「进程内状态清单」**派生**

新增 AST 哨兵：扫 `knot/` 的模块级可变状态（**按行为**：容器字面量 + 构造调用 + `@lru_cache` + `global`），
与一份**具名登记表**比对 —— **出现未登记的即红**，登记项须写明「多副本后果 + 为什么可接受 / 已处置」。
⚠️ **这是本片唯一防「下一片又漏一项」的东西** —— §0.1 已证明手写表漏了 3 项。

### ✅ D1（已拍板 2026-08-11）= **RWO** ⇒ **本片成立，作业面就是 §1 的 A/B/C/E**

⇒ §0.4 的实测（4 进程 × 200 写同一 WAL 库、零丢失零错误）**适用** —— 存储层没问题。

#### ⚠️ 但 RWO 带一个必须写进 DEPLOY 的运维前提（**转述 K8s 语义，非本机实测**）

`ReadWriteOnce` 的语义是「同一时刻只能被**一个节点**挂载读写」——
**同一节点上的多个 pod 可以共用**（K8s 后来加 `ReadWriteOncePod` 正是为了收紧到「一个 pod」）。
⇒ **多副本必须被调度到同一节点**，否则第二个 pod 会卡在挂卷失败（`ContainerCreating`）。

⇒ **两条运维登记**（本片写进 DEPLOY，不写代码）：
1. 扩容到 >1 副本时需保证**同节点共置**（pod affinity / 单节点集群 / `topologySpreadConstraints` 反向配置）——
   否则「多副本」根本起不来，**而那与本片修的东西无关**（别让运维把挂卷失败误读成本片的 bug）；
2. RWO 下**跨节点 RollingUpdate 不成立**（旧 pod 占着卷）⇒ 与现网已在用的 `Recreate` 策略**一致**
   （见记忆/DEPLOY：现网 = 关掉再起）。⚠️ 若哪天改回 RollingUpdate，须同节点 + `maxSurge` 评估。

⚠️ **我不声称**已验证现网真的做了同节点共置 —— 这条要运维侧确认。

### ~~D1（原问法）~~ 现网 PVC 是 RWO 还是 RWX/NFS？

- **RWO（多副本被迫同节点）** ⇒ §0.4 实测已证存储层安全 ⇒ R10' 作业面就是 §1 的 A/B/C/E，**本片成立**。
- **RWX / NFS（跨节点共享）** ⇒ ⭐ **WAL 跨主机不成立**（上游约束）⇒ 修进程内缓存**是修错了地方** ——
  存储层在任何写路径上都不安全，`platform_audit_repo.py:28` 已记过「首启并发写 ⇒ boot 崩循环」。
  ⇒ 那么 R10' 的真问题变成「**要不要换掉 SQLite**」，那是另一个量级的片。

**我的推荐**：先答 D1 再动手。若答案是 RWX/NFS，**建议本片改为「把多副本约束做成启动期强制」**
（K8s downward API 注入副本数 + 检测到 >1 副本且存储非本地 ⇒ fail-fast），
而不是修一堆在存储层就不成立的缓存 —— 那会**制造「已经安全了」的错觉**，比今天更危险。

### ~~D2（原问法）~~ `query` 限流（30/60s/user，防 LLM cost burning）怎么办？

| 选项 | 代价 |
|---|---|
| **(a) 也走共享计数器** | 与安全档同一套；query 频率高但**有本地阻断缓存兜底** ⇒ 写次数 ≤ 30/分钟/用户，**可接受** |
