### G3 · ⚠️⚠️ **本条的推论已撤回**（Codex R1 blocking · 我端到端复现证伪）

### G4 · 实测：非 owner 返 empty **不崩**，且 executor 确实不可达
模拟（patch `catalog._load_from_files` 返 empty 五元组，tid=2）：

### G17 · ⭐⭐⭐ 门必须装在 `execute`，不是 `pick_http_route`（守护者 Stage 1' 复核 · blocking · 我逐条实读）
| 事实 | 实读 |

`run_http_step` 签名 | `:446 async def run_http_step(refined_question, table_full_name, http_spec)` —— **spec 是参数收进来的** |

## §2 决议（Stage 1' · Codex 八条 + 守护者 §IV 九项已并入）

### D1 · file 层闸 = **外层 wrapper**（唯一 choke point，落在真路径上）
`catalog_loaders.py` 新增 `load_file_layer()`：内部调 `_load_from_files()`，
**非 owner 直接返完整 empty 五元组**。`catalog.reload()` 与 `get_defaults_from_files()` **都改调它**。
**无 ctx → `current_tenant()` raise**（fail-closed 且响亮；G6 已证生产无无-ctx 调用者）。
落点理由见 G8（放函数内部会被 4 处 facade patch 绕过 ⇒ 闸的 owner 路径零覆盖）。

### D2 · owner 侧 **「有效 tid=1 ctx 下行为等价」**（措辞已按 Codex R2 收窄）
~~byte-equal~~ → **有效 tid=1 ctx 下等价**：三层 `real→example→empty`、v0.7.29b file HTTP 权威覆盖、
`source_type` 推断、`_SOURCE` tag 全保持。
⚠️ **无 ctx 的行为是有意的契约变更**（原先可读 file → 现在 raise），**不得盖在 byte-equal 底下**。

### D3 · 非 owner → **完整 empty 五元组**（禁半空 · 理由已具体化）
`({}, [], "", [], "empty")`。**禁**只清 tables 留 lexicon/rules ——
G13 实读：`business_rules = db_rules if db_rules.strip() else f_rules` ⇒ **空-DB 的非 owner 会继续拿到
部署方业务口径**；`lexicon` 更是**无条件合并**。半空 = 泄漏口径 + 泄漏关键词映射。

### D4 · ⚠️ **验收反向**（Codex R3 · 与 R1 并列最重）
原草案验收 #7「给非 owner 的 DB catalog 灌 http 表 → `pick_http_route` **应命中**」
—— 那是**把绕过固化成绿色回归不变量**。**符号反了。**
⇒ **(b) 下反向为**：写入恶意 DB HTTP spec + lexicon 后，`pick_http_route` **仍 None**、executor **零到达**。
> 我的原直觉（「要证明 None 的**原因**」）是对的，**只是那时我以为原因是「槽空」；真原因必须是「门挡住」**。

### D5 · ⚠️⚠️ **清单措辞反向**（无论形状都必须做）
❌ **严禁**把 R-T-GATE 清单 ②③ 写成「结构性不可达」。
**为什么这是本片最危险的一处**：那会让**将来的 lift 建立在假前提上放行**。
⇒ 清单写法：**②③ 仍是 lift blocker**；当前状态 = 「**由 owner 门代偿**（D7）——
门是**临时代偿控制**，不是修复；②③ 落地时门被真凭据/真 egress 域化**替换**」。
⭐ **must（Stage 1' 复核）：光靠散文挡不住 lift** —— 做 lift 的人看到「blocker（代偿中）」
完全可能推理成「既然已代偿，lift 就安全」，正是 R-LP-v3-EX-3 要防的「承诺在阅读中蒸发」。
⇒ **加结构耦合**：CI 断言「**门存在 ⇒ R-T-GATE 未 lift**」⇒ 谁去 lift 就撞一条**点名这个门**的红测。
⭐ **形式必须是行为级，不是存在性**（Stage 1'' must-fix #4）：
断言「`assert_no_second_active_tenant_served` 的**调用点仍在**」只能抓**删除**，抓不住这四种
「**事实上 lift 了而行还在**」：`if False:` 包起来 · 把函数本体改 no-op ·
把调用点**移到 tid 解析之后**（不再是第一行 ⇒ 对平台/无 token 路径失效）· 前面插 early return。
⇒ **行为级形式**：插第二个 active 租户 → 请求**仍 fail-closed**，且失败消息**点名这个门**。
本仓 v0.9.4 那组 R-T-GATE 测已有两租户 setup ⇒ 成本近零，且免疫上述四种中和手法。
**你要排除的事件是「R-T-GATE 事实上不再生效」，不是「那一行不见了」。**
**先例**：v0.9.5 里 E1 的条件式靠 `test_iso4` 这条真 tripwire 自动触发（而非手册一句话）。

### D7 · ⭐⭐ **门装在能力行使处**（Stage 1' 复核 blocking · 已改）
**一个谓词、两个执行点**（不是两份判断 —— 多份**判断**才是「N 份清单」病）：

| 层 | 落点 | 行为 | 为什么在这 |
|---|---|---|---|
**硬边界** | `adapters/http/executor.py::execute` **函数内** | 非 owner → **raise**（fail-closed）| 它是**唯一**发出网络请求（G18：`requests.get/post` 两处都在它内）**且唯一读进程 env 凭据**的函数 ⇒ **能力就在这一行** |
**软降级** | `services/http_planner.py::pick_http_route` | 返 `None` + **记一行日志** | UX 与可诊断性：让查询**优雅落 SQL**，而不是 SSE 流中途 raise |

- **谓词单一真相源**：`knot/core/tenant_context.py` 加 **`OWNER_TENANT_ID = 1`** +
  **`is_owner_tenant() -> bool`**。三个消费点（`catalog_loaders.load_file_layer` /
  `http_planner.pick_http_route` / `adapters/http/executor.execute`）**全部 import 它**。
  ⭐ **落 `core` 是结构性唯一解、不是取舍**（Stage 1'' 复核 must-fix #2）：`.importlinter` 的
  `adapters-no-business` **禁 `knot.services`** ⇒ 谓词若放 `catalog_loaders`（services 层），
  **adapters 根本 import 不到** ⇒ `core` 是唯一合法的共享住所。
  ⭐ **改名的理由**：`core` 该知道的是「**谁是起源租户**」—— 那是**租户身份事实**
  （seed 硬编 + `tenancy_migration` 把 pre-tenancy `knot.db` 搬进它，G5）；
  而「**file catalog 归起源租户**」是**决定**，留在三个调用点的 docstring 里。
  这样 `core` 承担的仍是租户身份（它已在管 `current_tenant` / `tenant_cache_key` /
  `assert_tenant_context`），**不是 catalog 策略** ⇒ 我 §7 那条顾虑消解。
  额外好处：②③ 落地时要的正是同一个概念（「哪份凭据/allowlist 是部署方那份」），**不必再改名**。
- **今天零行为变化**：R-T-GATE 下被服务的只有 owner。
- ⭐⭐ **门的定性（Stage 1'' 复核 must-fix #1 · 我实读订正）**：门代偿的是 **②和③**，不只是 ②。
  凭据其实有**两条**路径，只有一条是进程全局的：
  | 路径 | 凭据来源 | 定性 |
  |---|---|---|
  `source_id`（`resolve_spec:411-441`，v0.6.1.4 **first-class**）| `data_source_repo.get_datasource` → **`get_conn()` = 租户库** + `_decrypt_ds_row`，注入**直填** `base_url`/`auth_*` | **已是 per-tenant 凭据**；指向别租户 id 在自己库里查不到 → `HTTPAdapterError` ⇒ **结构性安全** |
  env 引用（无 `source_id` → 透传，`execute:80-88` 读 `os.environ`）| **进程唯一一套** | **这才是 ② 讲的那条**（CLAUDE.md 原文指 `executor.py:87-88`）|
  ⇒ **钝门（全模式拦）过阻了 `source_id` 路径**。**让这个过阻仍然正确的是 ③，不是 ②**：
  `url_allowlist.py:24-33` 的 allowlist 是**进程级** ⇒ 非 owner 即便只用自己的凭据，打的也是
  **部署方 allowlist 里的主机** = 伸手进部署方网络（SSRF 向）。⇒ **门保持钝**，措辞改「代偿 ②③」。
  ⚠️ **可读性陷阱（实读发现）**：`resolve_spec` 的 docstring 是「模式 A(env)/B(source_id)」，而
  `executor.py` 的是「模式 A(直填)/B(env)」—— **两个模块的 A/B 指不同东西** ⇒ 本手册一律用
  **`source_id` 路径 / env 路径**，不用 A/B。
- ⭐ **门 docstring 必须写的前向耦合**：② 落地后最自然的动作是「现在非 owner 可以用 HTTP 了」——
  但**只有 ②③ 都落地才安全**。**门只能在两者都落地时移除**；否则有人在 ② 之后单独摘门而 ③ 还开着。
- ⚠️⚠️ **门的 raise 消息会到用户面前 —— 那正是 #262 那条缝**（实读：`run_http_step` 两处
  `except HTTPAdapterError as e: "error": str(e)` + 一处 `except Exception` 兜底 ⇒ 经
  `api/query.py` 原样 yield）。⇒ 消息**不得含 env 名 / owner tid / 部署方表名**，只说
  「该租户未启用 HTTP 数据源」；并挂一条断言到既有 `test_no_env_value_in_messages.py` 那套。
- ⭐ **额外好处（守护者指出）**：②（per-tenant 凭据）将来**正落在 `execute` 这条缝上**（它就是读
  `os.environ` 凭据的那个函数）⇒ **代偿控制与它的替代品占同一个接缝**，替换时结构上不会漏掉门。
- ⚠️ **软降级那半必须记日志** —— 否则非 owner 的 http 表被拒会**静默落 SQL**，正是 v0.7.29b 同型。
- **自我移除**：②③ 落地时，硬边界被真 per-tenant 凭据 + 租户域化 egress **替换**（不是叠加）。
