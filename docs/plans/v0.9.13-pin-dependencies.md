### F2' 只有 2 个包已有上界，且都是**因为踩过坑才加的**

`sqlglot>=30,<31`（v0.8.0 B6.1：AST 语义版本相关 = 安全承重）·`cryptography>=41,<46`。
⇒ 先例存在，且理由都是「上游变更会破坏承重行为」。

### F3' **三条安装路径全部汇入同一份** ⇒ 钉一处即全覆盖（**不是 N 份清单问题**）

| 路径 | 命令 | 最终读 |
|---|---|---|
| 镜像（= 现网） | `pip install -r requirements.txt`（`Dockerfile:13`） | `requirements.txt` |
| 本地 / CI | `pip install -e ".[dev]"` | `pyproject.toml:14` → `file = ["requirements.txt"]` |

### F4' ⚠️ **45 个传递依赖完全无约束** —— 钉直接依赖**不覆盖它们**

`.venv` 共 72 个包，直接声明 21 + dev 6 ⇒ **约 45 个传递依赖**由 pip 每次现场解析。
⇒ **只钉直接依赖，重建仍不可复现。**

### F5' 上游漂移打红 CI **已有 2 次实证**（记忆锚点 `knot-fastapi-0137-route-count-drift`）

FastAPI 0.137 路由计数 · ruff 0.16 `PLR0917` 转正式。
⭐ **kk 对 ruff 的处置是先例**：只在 **CI** pin minor 上界，`requirements-dev.txt` **保持浮动** ——
理由明写：「本地先撞新规则 = **早发现**」。⇒ **「CI 要不要也可复现」这个问题 kk 已经答过一次**，
而答案是「不要，我要早发现」。

## §2 设计（推荐 = 两层，与前端已有的做法同构）

⭐ **前端已经是对的形状**：`package.json`（范围）+ `package-lock.json`（精确）+ `npm ci`（照 lock 装）。
排练里正因为 lockfile 存在，**重建 bundle 才是可复现的**（与后端形成对照）。⇒ 后端照抄这个形状。

| # | 改动 | 为什么 |
|---|---|---|
| **d1** | **新增 `requirements.lock`** —— 全树精确 pin（含 45 个传递依赖），由 `pip freeze` 生成并**入库** | F4'：只有全树精确才真的可复现 |
| **d2** | **`Dockerfile:13` 改装 lock** —— `pip install --no-cache-dir -r requirements.lock` | ⭐ **镜像才是必须可复现的那个产物**（回滚靠它） |
| **d3** | `requirements.txt` **补上界**（`>=X.Y,<NEXT_MAJOR`），仍作 pyproject 的人读规格 | 让「声明」不再撒谎（现在它声称支持 `openai 1.x`，而从未测过） |
| **d4** | **CI 保持 `pip install -e ".[dev]"` 浮动** —— **刻意不钉** | F5'：kk 已就 ruff 拍过同一个问题，理由是「早发现」。**不推翻既有决策** |
| **d5** | **一条 CI 断言**：`requirements.lock` 里每个直接依赖的版本**必须满足** `requirements.txt` 的区间 | 防两份文件**互相矛盾**（这是引入第二份文件唯一的新风险） |
| **d6** | `DEPLOY.md` + `README` 运维段：怎么更新 lock（`pip freeze` 的确切命令 + 何时该做） | 否则 lock 会成为一条无人维护的散文规则 |

### ⚠️ 刻意不做（诚实收窄）

- **不上 `pip-tools` / `uv`** —— 会引入新工具链依赖；`pip freeze` 已够（本仓只有一个 Python 环境）。
- **不钉 `requirements-dev.txt`** —— 与 d4 同理（ruff 先例）。
- **不声称 CI 可复现** —— 刻意保持浮动，见 d4。
- **不声称「重建旧 tag 就安全了」** —— ⚠️ **lock 只对引入它之后的 tag 有效**；
  v0.9.12 及之前的 tag 重建**仍然不可复现**。**唯一可靠的回滚物仍是 `docker save` 的镜像**
  （排练已落 DEPLOY「🔴 回滚前置」，本片不改这条结论）。

## §6 待 kk 拍板（**1 项**）

**lock 的紧度**：我推荐 **d1 全树精确 pin**（`pip freeze`，72 行）。
**代价**：任何依赖升级（含安全补丁）都要**显式重生成 lock + 一个 commit**。
替代方案是只做 d3（补上界、不上 lock）—— 工作量小，但**重建仍不可复现**，
即 F1 那条真风险**没被消除**，只是收窄。
⇒ 我建议按推荐做；若你觉得维护负担不值，说一声我只做 d3。
