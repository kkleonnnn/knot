## §0 本片开工前发现的一个**既有**安全缺口（不是本片引入的，但本片会把它变成 API 可达）

**主租户库的路径解析没有含容校验**（`repositories/base.py:33`）：
```python
return Path(SQLITE_DB_PATH).parent / current_tenant()["db_dir"] / "knot.db"
```
无 `.resolve()`、无「在数据根内」判定，而紧接着 `get_conn()` 会
`p.parent.mkdir(parents=True, exist_ok=True)`（`base.py:44`）
⇒ **`db_dir='../evil'` 会在数据根之外建目录并创建主库** = OOS-1v2 文件边界逃逸。

⭐ **同形状的守护，它的两个兄弟都有**（⇒ 这是**不对称**，不是「本来就没这规矩」）：

| 路径 | 守护 |
|---|---|
| `uploads.db` **读侧** | `services/upload_engine.py:31-34` —— `root.resolve()` + `p.resolve()` + `root != p.parent and root not in p.parents` → raise「uploads 路径逃出数据根」 |
| C4 迁移 **写侧** | `repositories/tenancy_migration.py:342-346` —— 同形状（v0.9.2 Stage 4 对抗 critic 命中才补的） |
| **主库 `knot.db`** | ⛔ **无** |

**今天的可达性**：`db_dir` 无任何写端点（E2）⇒ 只有运维直改平台库能触到。
**本片把它变成 API 可达** ⇒ 故 **d2 的路径校验不是纵深，是堵一个本片自己会打开的洞**；
且 **d2' 必须同时给 `_tenant_db_path()` 补上兄弟们已有的那道守护**（纵深：写口校验只覆盖代码路径）。

### §1.1 ⭐ `db_dir` 取什么值 —— **本稿唯一的设计分歧，请 Stage 2/3 裁**

**约束**：`INSERT INTO tenants` 必须**恰一处**（kk ③）且 `UPDATE tenants` 已经**恰一处**
（`update_tenant`，哨兵 `tests/test_platform_audit.py:375`）
⇒ **不能**「先 INSERT 拿 `lastrowid` 再 UPDATE 回填 `db_dir`」——那会新增一个 UPDATE 站点，
或迫使 provisioning 复用 `update_tenant`（它自开连接 ⇒ **跨不了同一个事务**，破 v0.9.8 的
「审计与动作同事务」性质）。

**我的提案**：`db_dir = f"tenants/{slug}"` —— `slug` 是 `NOT NULL UNIQUE` 且**插入前已知**
⇒ 单条 INSERT 搞定，且 **`db_dir` 的唯一性由 `slug` 的唯一性派生**（d2 的 UNIQUE INDEX 成为**冗余保险**而非唯一防线）。
- ⚠️ **代价 1**：与既有约定 `tenants/1`（id 派生）**不同形**。tenant#1 保持原值不动 ⇒ 两种形态共存。
  可接受的理由：`db_dir` 是**不透明存储位置**，无人按它做标识（`core/tenant_context.py:108`
  明写「**`db_dir` 不可用作标识**」）。
- ⚠️ **代价 2**：`slug` 语义上**可改名**（同一处注释）⇒ 改名后 `db_dir` 与 `slug` 会分叉。
  **处置：`db_dir` 建成之后永不重写**（改名不搬数据）；这一点要写进 `db_dir` 列注释。
- **备选**：仍用 `tenants/<id>`，代价是必须在同一事务内做 INSERT+UPDATE
  ⇒ 需要为 `update_tenant` 增加「接受外部连接」的形参，或允许第二个 UPDATE 站点并调整哨兵。
  **我不倾向**：那会削弱两条已经立住的写口不变量，为的只是命名一致。

## §2 v3.1-B 承重面枚举（命中：鉴权 · 租户隔离 · 凭据 · 审计 · DB 迁移 · egress）

1. **fail-open 面**：`status` 若被调用方指定 ⇒ 传 `'active'` 即制造第二 active 租户 ⇒ **全站 fail-closed**（不是 fail-open，但是**拒绝服务**）。⇒ d1 **服务端强制** `'suspended'`，不读入参。
   `db_dir` 若可传 ⇒ §0 的逃逸变 API 可达（**真 fail-open**）⇒ d2 服务端派生 + d2' 纵深。
2. **oracle 能力 + 注入真能产生它吗**：
   - 「suspended 不可服务」的判据必须**行为级**（真发请求 / 真登录），不能只断 `status` 字面 —— 后者不能表示「解析器是否真的过滤」。
   - `db_dir` 逃逸的注入**真能产生后果**：实测 `get_conn` 会 `mkdir` ⇒ 断言「数据根外不得出现该目录」是可产生的事件。
   - ⚠️ UNIQUE INDEX 的注入需真的插两行同 `db_dir`；**且必须先证明既有 fixture 里没有同值**（见 #8）。
3. **「那一行」族**：
   - **门**在 `create_tenant()`（能力被行使处）+ `_tenant_db_path()`（路径真被解析处），**不在**端点层；
   - **记录**与动作**同连接、同事务、单次 commit**（照 `seed_default_tenant` 与 v0.9.8）；
   - **消息**：口令**永不**出现在任何失败消息里（诊断只说「已生成，见响应」）。
4. **（并入 #3）**
5. **散文规则**：「`db_dir` 建成后永不重写」是新散文 ⇒ 载体 = 列注释 + `update_tenant` 显式拒改 `db_dir`（**要有守护，不能只写注释**）。
6. **声明 vs 生产者**：新 action 不新增（复用 `platform.tenant_create`）⇒ Literal↔emit 集合等值不变；新端点的消费者 = 运维 + DEPLOY 文档（要写）。
7. **顶班**：摘掉 d2 的服务端派生后，d2' 的含容守护会**顶班**让测继续绿 ⇒ 两者的取材必须**各自单独**做（不能只测端到端）。
8. **既有测的绿是真的吗（扫两侧）**：⚠️ **UNIQUE INDEX 可能打红既有 fixture** ——
   `tests/` 里有 **10+ 处** 手写 `INSERT INTO tenants`（测绘 §2-3 列出），必须**逐处核** `db_dir` 有无重值；
   例如 `test_file_catalog_owner_gate.py:659-660` 是 `'tenants/1'` 与 `'.'`（不重，OK）。
   ⭐ 另须扫**断言侧**：有没有测在断言「`db_dir` 可以重复」这类现在要被禁掉的性质。
9. **契约冲突**：`INSERT` 恰一处 × `UPDATE` 恰一处 × 「同事务写审计」三者共同**排除**了「先插后补」
   ⇒ §1.1 的分歧**是这三条契约挤出来的**，不是命名偏好。**契约冲突常常在说结构错了** ——
   故我选「让 `db_dir` 不需要回填」而不是「放宽某条契约」。
10. **策略题的影子**：⚠️ **跨两个库的原子性**：平台库（租户行 + 审计）与新租户库（建表 + seed admin）
    **不可能同一事务**。⇒ 出现「两个都要我定策略」的味道。
    **处置（不是选策略，是选让失败留痕的那个顺序）**：**先写平台库（行 + 审计，单次 commit），再建租户库**。
    - 行在、库没建 ⇒ 该租户 **suspended 且不可见**（§2-1/2-2 实测）+ **审计里有记录** ⇒ 可发现、可重试；
    - 反序则留下**无人引用、无记录**的孤儿目录 ⇒ 不可发现。
    ⇒ 与 v0.9.8 同一条原则：**优先选择留下记录的失败模式。**
11. **诚实收窄**：见 §3。

## §3 本片**不**声称

1. **不放开第二租户服务** —— lift 仍是独立片；本片只让「租户存在」成为可能。
2. **不改** `resolve_single_tenant` 的 **7 处**生产调用点（lift 前置的另一项；d8 只把清单改成派生的）。
3. **不做租户删除 / 数据销毁**（append-only 审计 + 销毁语义，独立评估）。
4. **不声称运维直连 `sqlite3` 改平台库会被审计 / 被校验** —— 同 v0.9.8 边界，只声称**代码路径**。
5. **不声称口令投递安全** —— 只在**响应体**里返回一次；HTTPS 之外的投递（复制粘贴、日志转发）不在本片。
6. **不改前端** —— 平台面无 UI（v0.9.5 E1 的 out-of-band 密钥模型不变）。
