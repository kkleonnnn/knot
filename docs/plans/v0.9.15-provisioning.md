### §1.1 ⭐ `db_dir` = 服务端生成的不透明串（**推翻我上一稿的 `tenants/<slug>`**）

**上一稿错在哪（守护者 blocking）**：我提案 `db_dir = tenants/<slug>` 并声称「服务端派生、调用方不可传」
⇒ **那是空的**：`slug` **本身**由调用方传且**零格式校验**（自核：`platform_admin.py:135` 裸 `slug: str`）
⇒ `slug='../evil'` **把 §0 那条既有逃逸经新 API 完整复现**。
⚠️ 而**本仓 v0.9.7 已因同一前提否决过 slug 派生** —— 我重复了一个已被证伪的方向。

**改为**：`db_dir = f"tenants/{secrets.token_hex(8)}"`（服务端生成，调用方无输入面）。

| 性质 | 为什么成立 |
|---|---|
| 满足三条写口契约 | 插入前已知 ⇒ **单条 INSERT**，无需回填 ⇒ 不新增 UPDATE 站点、不破「审计与动作同事务」 |
| 零调用方影响 | 调用方**看不到也传不了**它 ⇒ 逃逸没有输入面 |
| **UNIQUE INDEX 从冗余保险变回真守护** | 唯一性不再由 `slug` 派生 ⇒ 索引是**独立**的第二道 |
| 与既有注释一致 | `core/tenant_context.py:108` 明写「**`db_dir` 不可用作标识**」⇒ 不透明正是它该有的样子 |

⚠️ **仍保留 d2 的含容校验与 d2' 的解析侧守护** —— 不因为「值是我们生成的」就省掉：
运维直改平台库仍可写入任意值（v0.9.8 同款诚实边界）。

### §1.2 ⭐ 可重试性（§I-2）—— §2-10 的顺序理由**全部建立在它上面**

**问题**：同端点重跑撞 `UNIQUE(slug)` ⇒ 「可重试」有一半是假的。

**处置：端点对「行已存在 + 库未建」幂等，且边界写死**：

| 状态 | 行为 |
|---|---|
| 无该 slug 行 | 正常开通（写平台库 → 建租户库） |
| 有 slug 行 + `suspended` + **租户库文件不存在** | **续做**：建库 + seed admin + 返回**新生成**的初始口令（库是全新的 ⇒ 口令也是全新的，不存在「改别人口令」） |
| 有 slug 行 + `suspended` + **库已存在** | ⛔ **不续做**，返回明确错误 + 指向 `reset_admin_password.py`（**不猜**该不该重置既有 admin） |
| 有 slug 行 + `active` | ⛔ 拒绝（不碰在服务的租户） |

⚠️ **判据必须是「库文件是否存在」而不是「users 表是否为空」**：后者要先建连接，而
`get_conn()` 会 `mkdir` + 创建文件 ⇒ **测量动作本身会改变被测状态**（本弧第 ⑤ 条形状的近亲）。

### §1.3 ⭐ `suspended` 租户的库怎么建（§II-3 —— 草案通篇没写，本片最静默的一处）

**实测约束**：`resolve_tenant_by_id` 对 `status != 'active'` 返 `None`（`tenant_repo.py:195`）
⇒ **走解析器拿不到 ctx**，而 `get_conn()` 需要 ctx。

**唯一可用路径**：`get_tenant()`（**刻意不过滤 status**，`:105`，B-2 承重注释写明理由）
\+ `set_active_tenant()`。但那是**第二个 ctx 生产者** ⇒ **三条必须同时**：

1. **只在 `create_tenant()` 内部**（不导出、不给别处用）；
2. **`try/finally: reset_active_tenant(token)`** —— `set_active_tenant` docstring 明文要求
   （自核已引：「防 ctx 泄进 serving 使 fail-closed 虚化」）；
3. **配一条测断言 ctx 不泄漏进后续请求** —— 且**建库中途失败**的分支也要测
   （⚠️ 与 §2-10 的顺序耦合：建库跑在一个**从 suspended 行造出来的 ctx** 里；
   中途失败而未 reset ⇒ **后续请求带着一个不可服务租户的 ctx**）。

⭐ 本仓已有同族先例可循：`main.py` 启动序三处 `set_active_tenant(...)` + CLI 脚本四处，
**都是 set 后 finally reset** 的形状。

## §2 v3.1-B 承重面枚举（鉴权 · 租户隔离 · 凭据 · 审计 · DB 迁移 · egress）

1. **fail-open 面**：`status` 若读入参 ⇒ 传 `active` 制造第二 active 租户 ⇒ 全站拒服务（非 fail-open 但是 DoS）⇒ d1 服务端强制。
   `db_dir` 若可传（**或可由零校验的 slug 派生**）⇒ §0 逃逸 API 可达 = **真 fail-open** ⇒ §1.1 + d2 + d2' 三层。
2. **oracle 能力 + 注入真能产生它吗**：
   - 「suspended 不可服务」须**行为级**（真发请求 / 真按 slug 登录），不能只断 `status` 字面 —— 后者表示不了「解析器是否真的过滤」。
   - `db_dir` 逃逸的注入**真能产生后果**（`get_conn` 会 mkdir）⇒ 「数据根外不得出现该目录」是可产生的事件。
   - UNIQUE INDEX 的注入须真插两行同值，**且先证明既有 fixture 无同值**（见 #8）。
   - **ctx 泄漏**的 oracle 必须是「**后续请求**看到的 ctx」，不是「函数返回后读一次变量」。
3. **「那一行」族**：门在 `create_tenant()`（能力行使处）+ `_tenant_db_path()`（路径真被解析处），**不在**端点层；记录与动作**同连接同事务单次 commit**；**口令永不出现在任何失败消息里**。
5. **散文规则**：「`db_dir` 建成后永不重写」须有守护（`update_tenant` 显式拒改 `db_dir`），不能只写注释。
6. **声明 vs 生产者**：不新增 audit action ⇒ Literal↔emit 集合等值不变；新端点消费者 = 运维 + DEPLOY（要写）。
7. **顶班**：摘掉 §1.1 的服务端生成后，d2/d2' 会**顶班**让测继续绿 ⇒ 三者取材**各自单独**做，不能只测端到端。
8. **既有测的绿是真的吗（扫两侧）**：
   - ⭐ **`test_iso6b_no_write_methods_under_platform_prefix` 按设计必红** —— 它挡的是**整个前缀的写面**，正是 E2 的载体。
     ⭐ **它自己的失败消息就写明了解锁条件**：「**要加写端点，先做平台审计落点（B-3 之后）**」
     ⇒ v0.9.8 已给落点 ⇒ 改成**精确 allowlist** 是**兑现它写明的条件**，不是放宽它。
     ⚠️ **必须是「精确等于恰一条具名写端点」**，**不得**放宽成「允许前缀下有写方法」——
     后者会让第二条写端点悄悄进来，**而那条测的全部价值就是拦住它**。
   - `test_iso4`（platform.db 表集精确等于 `{tenants, platform_audit}`）**不受影响** ——
     UNIQUE INDEX 是 `type='index'` 非 `'table'`（守护者已核）。
   - **路由计数 +1**：flatten 计数 + 策略快照新键归 `PLATFORM_SECRET` 类。
   - ⚠️ **UNIQUE INDEX 可能打红既有 fixture**：`tests/` 有 **10+ 处**手写 `INSERT INTO tenants`
     ⇒ 逐处核 `db_dir` 重值（实施期第一件事）；**并扫断言侧**有无测在断言「db_dir 可重复」。
9. **契约冲突**：`INSERT 恰一处` × `UPDATE 恰一处` × `同事务审计` 排除了「先插后回填」
   ⇒ §1.1 的取值是这三条挤出来的。⚠️ 而 §II-2 揭示 **kk③ 那条本身与现状冲突** ——
   处置不是去动 seed 的 status（tenant#1 必须 `active`），而是**把判据改成精确集合**
   `{seed_default_tenant, create_tenant}`：保住 kk 真正要的性质（**第三处不得静默出现**）且与现实相符。
10. **策略题的影子**：跨两库不可能同一事务 ⇒ **不选策略，选留痕的顺序**：
    平台库（行 + 审计，单次 commit）**先**，租户库**后** —— 行在库没建 ⇒ suspended 不可见
    \+ **审计有记录** ⇒ 可发现、**且经 §1.2 真的可重试**；反序留下无人引用也无记录的孤儿目录。
11. **诚实收窄**：见 §3。
