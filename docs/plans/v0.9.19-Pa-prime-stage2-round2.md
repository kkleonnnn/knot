## §B ⭐ 最值钱的一条：**派生覆盖的强项与代价，是同一个性质的两面**

我在 P-a 里建了三条「派生覆盖」，卖点是「**第三份 allowlist 会被自动拉进来**」。
重写版据此写了「§D2 几乎白送」。

**实测（我自己跑的）**：只把 `allowed_db_hosts` 加进 `_MUTABLE_TENANT_FIELDS`、**其余什么都不做** ⇒
```
15 failed, 24 passed
```
且其中**包括既有两列自己的守护测**：
```
FAILED …test_every_allowlist_has_a_startup_env_fallback_warn[allowed_http_hosts]
FAILED …test_every_allowlist_has_a_startup_env_fallback_warn[allowed_webhook_hosts]
```
（因为断言是 `n_calls >= len(_MANAGED)` ⇒ 加一列后 **2 >= 3** 不成立。）

⇒ **那三条派生测把「所有 allowlist 列必须**完全同构**」编码成了硬约束。**
而 kk ② 恰恰要求第三列**不同构**（不新造 env 回退）。

> ⭐ **「新成员自动被拉进覆盖」与「新成员必须与既有成员完全一样」是同一条断言的两面。**
> 我卖它的时候只说了第一面。

⇒ **判据升级**（建议折进 CLAUDE.md）：
> 建「派生覆盖」时必须同时回答：**这条派生把哪些差异变成了非法？**
> 若将来的合法成员可能在某个维度上不同，**那个维度就不能进派生断言的相等部分**
> —— 否则第一个合法的例外会同时打红所有既有成员。

## §C 阻断项（全部已自核 ✅）

### C0' · ⛔ **活缺陷**：`db_database` 可覆盖 host ⇒ 门校验的值不决定去哪
**我的实测**：
```
url.host（门会校验的）  = 'allowed.corp'
真正的连接实参 host    = 'evil.example.com'
```
`build_connection_url`（`adapters/db/doris.py`）用 **f-string** 把 `database` 拼进 URL；
`db_database` 是**同一个表单里的自由文本**，租户 admin 可填
`db1?host=evil.example.com&charset=utf8mb4#`。

⚠️ **诚实定级**：**今天不是可利用的洞**（`db_host` 本来就随便填，从这里绕没有额外收益）。
⛔ **但它让本片正要建的门从第一天起可绕过** —— 这是本仓自诊断的教科书形态：
> **门校验 `host` 形参，而决定去哪的是 `create_connect_args` 的输出。判据锚错了对象。**

⇒ **修法**：URL 改 `URL.create()` **按组件构造**（注入原理上不可能），**优于**在门里加过滤
—— 后者消灭一个 payload，前者消灭这一类。

### C1' · ⛔ 「白送」是假的，且它会打红既有两列
见 §B。⇒ **真实工作量 = 改那三条共享测**，而**改它们会削弱现有两列的守护** ⇒ 必须明码标价。

### C2' · ⛔ seed 放迁移里在**真实升级路径上一次都不跑**
**我的实测**：全新 `platform.db` 经 `executescript(platform_schema.sql)` 后
`tenants` **已含**三列 ⇒ `if col not in cols:` **全部跳过**。
而现网 v0.6.1.4 升级会**全新创建** `platform.db`（DEPLOY 自己写着两条平台迁移都是 no-op）。
⇒ seed 若写进 ALTER 块：**测里绿**（测造的是手工缺列的老库，走 ALTER 路径）、**现网一次不跑**。
⭐ **这是五问⑤**：测里的库是 `ALTER` 出来的，现网的库是 `CREATE` 出来的 —— **两边不同法产出**。

**另**（lens C 实测）：`run_platform_migrations` 那一刻 `tenants` 行数 = **0**
（`seed_default_tenant` 在其后）、租户库文件**尚不存在**（C4 在其后）
⇒ 平台连接读 `data_sources` = `no such table`。**seed 在那个位置原理上做不到。**

### C3' · ⛔ §4-1/2 的 oracle 恒为 0（空判据）
**lens A 实测**：`post=200 naive_rowcount=0 correct_rowcount=1`。
`list_datasources()` 走 `get_conn()` 读**测体自己的 ctx**（autouse = tenant#1），
而行落在 tenant#2 的库 ⇒ 「断 0 行」**摘门后仍是 0**。
⇒ 必须先 `set_active_tenant(get_tenant(2))` 再读。

## §G ⭐ 对比第一轮：哪些真修好了，哪些是换了形状的同一个错

| 第一轮的阻断 | 重写版 | 判定 |
|---|---|---|

⛔⛔ **同一个错，两轮，两种形状**：

| | 第一轮 | 第二轮 |
|---|---|---|
| 我写的「已验前提」 | 「`main.py`/`repositories/`/`scripts/` 0 处调用 ⇒ 没有无 ctx 的路径」 | 「迁移期 seed ⇒ 升级零断」 |
| 实际 | 扫的是**文件位置**，而无 ctx 的路径由**线程**制造 | 那段迁移代码**在真实升级路径上一次都不跑** |
| **共同点** | **我验证了「代码写成什么样」，没验证「它在真实执行路径上会发生什么」** | 同 |

⇒ **这不是细节没写够，是我的验证习惯有一个固定的盲区。**
⇒ 建议 Stage 3 追加**第三条放行硬条件**：
> **凡声称「某段代码会跑」的，必须给出它在真实路径上被执行的证据**
> （不是「它在文件里」，也不是「有测覆盖它」—— 测可能与生产不同法产出）。

⚠️ 而这条与我今天已犯的另外三次（管道吞输出 / `python3` 不是 venv / 后台命令 stdout）**是同一件事**：
**我倾向验证「我做了什么」，而不是「系统真的变成了什么」。**
