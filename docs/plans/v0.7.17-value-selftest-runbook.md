## 1. metric 定义（8 原子 + 2 派生 · 全挂 `ohx_ads.ads_operation_report_daily` 日级聚合表）

> 该表**一行/UTC日期**（无渠道/品种下钻维度）→ 维度仅 `sta_date`；加性指标 `SUM(field)` 在日期窗内**正确**。
> 日期列 = `sta_date`（v0.7.17 显式 `date_column` 注入；旧正则 miss 的就是它）。caliber 用别名 `o.`（编译器 `FROM ... o`）。

| name | display | caliber | date_column | aliases | 备注 |
|---|---|---|---|---|---|
| `deposit` | 充值 | `SUM(o.deposit)` | sta_date | 充值,入金,充值金额,deposit | 加性 ✓ |
| `withdraw` | 提现 | `SUM(o.withdraw)` | sta_date | 提现,出金,withdraw | 加性 ✓ |
| `net_deposit` | 净充值 | `SUM(o.net_deposit)` | sta_date | 净充值,净充 | 加性 ✓ |
| `reg_users` | 注册数 | `SUM(o.reg_user_num)` | sta_date | 注册,新增注册,注册用户,新用户 | 日新增求和=区间新增 ✓ |
| `future_amt` | 合约成交额 | `SUM(o.future_match_amt)` | sta_date | 合约成交额,合约交易额,永续成交 | 加性 ✓ |
| `future_fee` | 合约手续费 | `SUM(o.future_fee)` | sta_date | 合约手续费 | 加性 ✓ |
| `platform_pnl` | 平台盈亏 | `SUM(o.platform_pnl)` | sta_date | 平台盈亏,平台盈利,平台亏损 | 加性 ✓ |
| `active_user_days` | 活跃人日 | `SUM(o.active_user_num)` | sta_date | 活跃,活跃用户,DAU | ⚠️ SUM=活跃**人日**≠月活去重（日表聚合性质；§6 caveat）|
| `net_deposit_rate` | 净充率（派生）| —（lineage）| — | 净充率,净充占比 | `net_deposit ÷ deposit`（divide→NULLIF）|
| `future_fee_rate` | 合约费率（派生）| —（lineage）| — | 合约费率,手续费率 | `future_fee ÷ future_amt` |

派生 lineage：
- `net_deposit_rate` = `{"op":"divide","left":"net_deposit","right":"deposit"}`
- `future_fee_rate` = `{"op":"divide","left":"future_fee","right":"future_amt"}`

## 4. 自测问法（10-20 句 · 覆盖「应命中」+「应回退」两类）

**应命中（确定性编译）** —— 时间窗 + 注册 metric：
1. 本月充值多少
2. 昨天净充值
3. 近 7 天合约成交额
4. 这个月平台盈亏
5. 本月注册数
6. 每天的充值（趋势 → GROUP BY sta_date）
7. 本月合约手续费
8. 上周提现
9. 本月净充率（派生）
10. 这个月合约费率（派生）

**应回退（语义层边界 —— 验回退优雅 + parser 不乱命中）**：
11. 查 user 12345 的当前持仓（→ HTTP futures_admin 跨源 OOS）
12. 各国家的注册数（→ 需 dwd 明细 country 维度，本 seed 全是 ads 日级聚合，无此 metric）
13. 充值最多的 10 个用户（→ 按用户明细 dwd，无 metric）
14. 理财余额（→ business_rules「该数据暂未开放查询」）
15. 帮我写个 SQL 查 xxx（→ 非指标问法）

## 5. 观测（命中 vs 回退）

- **AdminLogicForm 审计屏**（admin → LogicForm 审计）：每条查询留痕 —— `engine=semantic`（命中）vs near-miss（回退 + reason）。
- **命中条**：看编译 LogicForm + SQL —— 时间窗是否正确注入 `o.sta_date BETWEEN '...' AND '...'`（v0.7.17 修复点）；caliber 是否 `SUM(o.xxx)`。
- **回退条**：near-miss reason（parser 没出 LogicForm? metric 没覆盖? 编译 raise?）。
- **数据正确性**：命中条的 SQL 丢 Doris 实跑，核对数字（尤其时间窗边界 = D-1 数据延迟，最新 sta_date=昨天）。

## 6. caveats（自测会暴露的语义边界 —— 这些是「正确的回退/限制」非 bug）

1. **`active_user_days` SUM = 活跃人日 ≠ 月活去重**（日表 active_user_num 按天，求和双计跨天活跃用户）。月活去重须 `ads_operation_report_monthly`（字符串区间日期 → 当前 OOS）。**这正是注册表「显式口径」价值** —— 口径歧义由 admin 明确定义，不靠 LLM 猜。
2. **weekly/monthly 表字符串区间日期**（`'YYYY-MM-DD~...'`/`'YYYY-MM'`）→ BETWEEN 不可比 → 本 seed 不含（OOS，未来刀）。
3. **跨源 HTTP `futures_admin`**（持仓/挂单）→ 语义层 OOS（`compile_helpers` raise）→ 回退 LLM。
4. **明细/按用户/按国家** → `ohx_dwd` 表，本 seed 全是 `ohx_ads` 日级聚合 → 不覆盖（可后续加 dwd metric）。

## 7. 记录什么（回报 → 定下一刀）

- **命中率** = 命中数 / 应命中数（问法 1-10）。
- **回退分类**：每条回退 → parser 未出 LogicForm（命中识别弱）/ metric 未覆盖（注册不全）/ 编译 raise（覆盖 gap）。
- **编译 SQL 正确性**：时间窗注入对不对、口径对不对、数字对不对。
- **新 gap**：哪些日常问法既该命中又没命中 → 下一刀优先级（如 parser prompt 教学加强 / metric 扩注册 / 编译覆盖补）。

> 这一轮 grounded 数字（而非推测）才能定「编译覆盖够否、转 parser 命中率优化、还是转部署」。
