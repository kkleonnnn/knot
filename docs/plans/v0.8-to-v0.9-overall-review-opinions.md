## 产物 4 — v0.9 多租户预期范围骨架（非锁定）

### 三个必须资深拍板的决策点
1. **数据形态**：**推荐 C = 平台库 + per-tenant SQLite 文件**（fail-closed 隔离，把泄漏面从"每条 SQL 的 WHERE"收敛到"租户上下文解析单点"；BI「全员可读」读路径零重写；单写者瓶颈/per-tenant 备份/租户下线删数一并解决）。次选 A 行级 tenant_id（需配 SQL 过滤 CI 审计，仅当租户数 ≤3 且时间紧）。B schema-per-tenant 在 SQLite 下排除。**不建议**「换 Postgres + 多租户」同一 MINOR 双大手术。
2. **admin 语义拆分**：平台 admin vs 租户 admin。实测 `require_admin` **88 处 / 22 文件**（盘点初估 ~30 显著低估）——逐端点归类是 v0.9.1 主工作量。叠加 `KNOT_TOTP_BYPASS_ADMIN` 现豁免**所有** admin，须收窄到平台 admin。
3. **计费边界**：OR key 平台统付（成本按 `users.monthly_cost_usd` SUM 出租户账单）vs 租户自带 key（per-user fallback 列已是演进锚点）。

### catalog ≠ tenant，但结构高度可复用
`tenant 1—N catalog`。C 方案下 catalogs 落租户库即天然归属，**`metric 归 catalog_id` 整条语义链零改动继承**——OOS-1 当年把 catalog_id 定义为「水平切分 ≠ 租户隔离」的先见在此兑现。catalog ContextVar 模式复制为 tenant ContextVar 供 get_conn 解析。

### 跨租户泄漏风险 Top 5（v0.9 必须逐一堵）
1. **catalog 全局回退 + HTTP helpers 直读全局 TABLES**（catalog.py:27-31/:200-244 绕 ContextVar）——非 query 路径永远读"某一租户"的表结构/规则/lexicon 注入他租户 prompt。
2. **LLM prompt 装配面零归属**：knowledge_docs/doc_chunks + few_shots 全局注入所有用户 → A 租户业务文档/SQL 样例喂进 B 租户上下文。**不走 DB 读路径，常规资源鉴权抓不到**，须在 prompt 装配层单设租户断言。
3. **BI 读路径全员可见 + 分享目标全局**：list/get 无归属过滤（单报表 GET 连 view 门都无）+ bi_share_targets 全局 chat_id 白名单。
4. **JWT 无租户 claim + 单层 admin**。
5. **进程内单例/全局兜底群**：`_DS_STATS_CACHE` 单槽 · engine_cache 无归属校验 · 全局默认 DB_* 兜底（未配源用户静默连别人的库）· budgets global/all fallback（一租户烧钱全实例熔断）。

### OOS-1 修订仪式要点
OOS-1 是 **CI 主动守护的死线**（schema.sql 8 处内嵌注释 + test_catalog_repo/test_monitor_repo/test_metric_repo 等结构断言群 + CLAUDE.md 不变量条目）。**加 tenant 概念的第一个 commit 之前必须先走仪式翻转守护，否则 CI 直接红**。C 方案红利：租户库内表的「严禁 tenant_id 列」断言**大多不翻转、只改措辞**（新语义=隔离靠文件边界）；行级方案则 8 处全翻。

### 🐢 全局体验痛点：每次导航/刷新，动态数据全部清空重等（kk 亲述 · 专项 workflow 诊断，全 code-verified）
> **症状**（kk）：每次首进首页/次级页/刷新，之前加载的一切「后端生成的数据」（对话/报表/数据源/用户/角色/API Key/上传/few-shot/prompt/知识库/指标目录…）都清空并长时间重载；只有写死的静态 UI 骨架秒出。

**定性：主因是感知延迟（前端架构），不是后端慢。** 「静态骨架秒出、所有数据都重等」是教科书级 **refetch-on-mount 指纹** —— JS 已暖、外壳已在，但每个数据区在每次组件挂载时从空 `useState` 从零起步、重新 fetch、无缓存兜底、无骨架保留旧值。若后端普遍慢，静态骨架不可能秒出。

**三条前端根因（叠加 → 全屏症状，全部 code-verified）**：
1. **零客户端数据缓存**：全仓无 SWR/react-query/Context/fetch 缓存（`api.js` 最薄封装）；`usePersist`（`utils.jsx:113-122`）只存"选了哪个"的**指针**（会话 id/报表 id），不存数据本体 → 数据没变也每次重拉。
2. **切屏 = 卸载重挂，无 keep-alive**（`App.jsx:144-168` 单屏条件渲染）：出屏即销毁全部局部 state，新屏从空值起步。"清空"不是 `setX([])`，是组件被整棵丢弃重建。
3. **无骨架屏 / 不保留旧数据**（BI 连 loading flag 都没有，`BI.jsx:65-98`；`cb_bi_report` 存了选中 id，加载时主区却先闪"选择左侧报表"占位）。

**刷新（F5）再叠两道硬串行闸门**：① `me()` 返回前 `App.jsx:106` 用居中 Spinner 挡住整个外壳；② ~1.08MB 首屏 JS（含强制随首屏的 553KB echarts，无懒加载，`Shared.jsx:11`）+ `/assets` 无 immutable 缓存头（`main.py:240` → 每次刷新对 1MB 资产做 304 协商）。

**后端真慢只集中两处**（不构成"一切都慢"）：`GET /api/admin/datasources` 逐源实时建连探测且零缓存（一源宕拖 +3~5s，被 App+BI+Admin 三处重复调，`datasources.py:22-64`）· `GET /api/bi/reports` 列表 `SELECT *` 把每个报表全量冻结快照（≤1 万行/报表）inline 下发（`bi_report_repo.py:128-136` + `bi_report_service.py:308-322`）。

**修复阶梯（按 感知收益/工作量）**：
| | 修复 | 效果 | 风险/量 |
|---|---|---|---|
| 🥇 R1 | `api.js` 加轻量 **SWR（stale-while-revalidate）缓存 + in-flight 去重** | **一处改动覆盖全部屏**：从"每次从零长等"→"瞬时显示旧数据 + 后台静默刷新"；顺带消除数据源三处重复调 | 中；api.js 在 byte-equal 守护清单 → 须明确 scope PATCH |
