### 0.2 ⭐ 实测推翻 v0.9.18 草案 §5 的第 1 步

那份草案写着：「**先**删 `test_two_tenant_e2e_isolation.py` 的 monkeypatch，其余一律不动 → 跑该文件。
全绿 ⇒ 预演可信，继续；**有红 ⇒ 停**」。

**实测结果**（外部 pytest 插件在 `pytest_runtest_call` 把真门装回去 = 等价于删掉那行 monkeypatch，
**仓库零改动**）：

```
18 failed, 3 passed
```

**原因是结构性的、不是环境问题**：门是 `resolve_for_request` 的**第一行**，而该 fixture 造的正是
**2 个 active 租户** ⇒ 门必然触发 ⇒ **每个 HTTP 请求 fail-closed**。
⇒ 那一步**必然红**，然后按它自己的判据「有红 ⇒ 停」把自己停掉。

**仍绿的恰好 3 条，且恰好都是不走 HTTP 请求的**（交叉印证同一个成因）：

| 仍绿 | 为什么 |
|---|---|
| `test_two_tenants_really_use_distinct_db_files` | 直接查库文件 |
| `test_interim_tid_selects_the_tenant_for_2fa_path[1]/[2]` | 走 `interim_session`，不经请求级租户解析 |

⇒ ⭐ **修正**：**门那一行与 monkeypatch 必须一起删** —— 它们是同一件事实的两半，
拆开跑没有任何一步是有意义的。（§4 已按此重排。）

### 0.3 ⭐⭐ 新发现：lift 后「激活第二家」**没有任何代码路径**

AST 实测（属性调用 / 裸名调用 / import 三种形态全扫）：
**`tenant_repo.update_tenant` 生产调用方 = 0**，只有 `tests/test_platform_audit.py` 与

而 `update_tenant` 正是 v0.9.8 建的**单一写口**（审计 INSERT 与动作**同连接、同事务、单次 commit**，

### 0.4 ⭐ 新发现：一条**只写在 docstring、零守护**的规则，且它的理由 lift 后会失效

## §1 核心判断：lift 不是「删一行 + 补回归」，是**把一条已存在的预演转正**

`test_two_tenant_e2e_isolation.py` **现在就在**双 active 租户下跑端到端隔离
（token 只读自己家 / 库文件分离 / tid 篡改 401 / 代号选租户 / 审计落对库 / 2FA interim 选租户…）。

⇒ **lift 最强的验收不是新写的测，而是那 21 个函数在门真的没有了之后仍然全绿。**
⇒ 本片的风险因此**不在「双租户能不能跑」**（已答），而在 §2 那个判据问题。

## §2 ⚠️ 本片最容易做错的地方：lift 后「门被误删」与「门按计划删了」在行为上完全一样

⇒ **换判据的原则**：新判据必须回答**新的那个问题** ——

> **两个 active 租户下，A 的 token 能不能读到 B 的数据？**

而**不是**「那行代码还在不在」。这是本仓那条自诊断的又一次应用：
**判据要锚在系统真的产出了什么。**

⚠️ **删掉旧测是错的** —— 它们的**断言**仍值钱，过期的只是**理由**
（v3.1-B #8：「处置通常是改名 + 重写理由，不是删」）。

### §3-C ⭐ 激活 CLI（**kk 2026-08-10 裁定选 B**）

**为什么需要它**：§0.3 实测 —— lift 后「把某家改成 active」是整个平台影响面最大的动作，
而它**没有任何代码路径** ⇒ 只能直接 `sqlite3 UPDATE` ⇒ **不留痕**，
同时 v0.9.8 专门为它建的审计写口 `update_tenant` **零调用方**。

**设计**（照本仓既有纪律，不自创）：

| 项 | 内容 | 依据 |
|---|---|---|
| 载体 | `knot/scripts/set_tenant_status.py` | 与 `reset_admin_password` / `purge_audit_log` 同族 |
| 写路径 | **必须**经 `tenant_repo.update_tenant` | v0.9.8：审计与动作同连接、同事务、单次 commit ⇒ 不存在「做了但没记」 |
| 目标 | `--tenant <id>` **必填、无默认、缺参零写入 + 非 0 退出** | CLAUDE.md v3.1-B #1：**破坏性工具不得有默认目标**（v0.9.15 三个实例的教训） |
| 状态 | `--status active\|suspended` 必填 | 不给默认 —— 「默认激活」正是最危险的那个默认 |
| 预览 | `--dry-run` 可保留回退，但**必须打印它解析到了谁** | 同上条的但书 |
| 起源租户 | 停用起源租户仍由 `update_tenant` 内既有守卫拒绝 | v0.9.6 已立，本片**不动它** |
