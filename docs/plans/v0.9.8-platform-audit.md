## §0 grounded 事实基座

### 0.1 为什么平台动作今天无处落审计

| 事实 | 依据 |
|---|---|
| `audit_service.log` → `audit_repo.insert` → `get_conn` = **租户库** | `audit_service.py:127` 一带（含 `reraise_if_tenant_error`） |
| 平台动作（建/停租户、改 `db_dir`）**没有租户库可写** | v0.9.5 E2 决策原文即此 |
| ⇒ v0.9.5 **刻意零平台写操作**，理由就是「平台动作没有审计落点，而『建/停租户』正是最需要审计的动作」 | `tests/test_tenant_isolation.py:195-198`（该决策被写成一条测的失败消息） |
| ⇒ **R-10 audit-on-drift 因此至今未解开** | CLAUDE.md R-T-GATE 段 |

### 0.2 ⚠️ 全仓**没有**「每 Literal ≥1 emit」的全局 CI —— 只有按前缀硬编的守护

- `tests/api/test_metric_invariant_guards.py:74`（`metric.*`）+ `:94`（`bi_report.*` / `bi_permission.*` /
  `report_folder.*`）。该文件 `:86` 的注释原文：「守护者 Stage 3 §C：**无「每 Literal ≥1 emit」全局 CI**
  （唯本文件硬编 `metric.*`）→ BI 显式扩」。
- ⇒ **本片必须自建 `platform.*` 前缀守护**（照该先例），**且**由此得出一条硬约束（见 D2）：
  **只声明本片有生产者的 Literal**。

### 0.3 ⚠️ 加表会打红一条既有测（by-design，必须预先声明）

`tests/test_tenant_isolation.py:203` `test_iso4_platform_db_only_tenants_table` 断言
**`platform.db` 表集 == `{tenants}`**（「防业务表漂回平台库 —— 平台库最小化起步」）。
⇒ 加 `platform_audit` 表**必然打红它**。处置见 §4.3（**不是**放宽成 `>=`，而是改成精确的二元集合 +
把「为什么这张表是平台库的合法居民」写进失败消息）。

### 0.4 本片可用的**真实生产者**只有一个（D-A=CLI 的连带后果）

| 候选动作 | 今天有代码路径吗 | 归属 |
|---|---|---|
| 租户**创建** | ✅ `tenant_repo.seed_default_tenant()`（首启建 tenant#1） | **P1** |
| 租户**停用 / 启用 / 删除** | ❌ 零代码路径（D-A 选 CLI ⇒ 开通/停用脚本在 **P2**） | **P2** |
| **改 `db_dir` / 改 `allowed_http_hosts`** | ❌ 今天是运维**直接 `UPDATE`**（DEPLOY.md 记为唯一途径） | **P1 提供 choke point**，P2 的 CLI 成为主生产者 |

⇒ **这是 v0.9.5 E4「零消费者 = 死码」陷阱的镜像形态**：若本片把生命周期四个动作的 Literal 全声明了，
其中三个**永不 emit** ⇒ 前缀守护必红，或者只能把守护写松（那就等于没守护）。**必须只声明有生产者的。**

### 0.5 既成范式（照抄，不发明）

- **审计写入**：`audit_service.log(*, actor, action, resource_type, resource_id, success, detail, …)`
  + `audit_repo.insert(...)`（`audit_repo.py:15-29`，13 个命名参数）。`actor: dict | None` ⇒ **允许 None**
  （平台动作无登录用户：首启 seed / CLI 运维）。
- **平台库连接**：`tenant_repo.get_platform_conn()` —— **ctx-free**（不经 fail-closed `get_conn`），
  正是为「启动序 / 平台面」设计的。
- **平台迁移**：`tenant_repo._run_platform_migrations()`（**v0.9.7 刚建**）—— 本片是它的**第二个用户**
  （加 `tenants.updated_at`），顺带验证那套机制不是一次性的。
- **审计 fail-closed**：v0.9.4 MF3 教训 —— `audit_service.log` 曾 fail-soft 吞 `TenantContextError`
  ⇒ **安全记录静默丢失**。平台版**不得**重犯。

## §1 决议（D1–D8）

### D1 新平台表 `platform_audit`（platform.db）

```sql
CREATE TABLE IF NOT EXISTS platform_audit (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    ts           TEXT    NOT NULL DEFAULT (datetime('now','localtime')),
    actor        TEXT,            -- 'system:boot' / 'ops:<whoami>' / NULL（平台动作无登录用户）
    action       TEXT    NOT NULL,-- PlatformAuditAction Literal（见 D2）
    tenant_id    INTEGER,         -- 动作的对象租户（NULL = 非租户维动作）
    tenant_slug  TEXT,            -- 冗余存快照：租户被删/改名后审计仍可读
    success      INTEGER NOT NULL DEFAULT 1,
    detail_json  TEXT,            -- JSON；⚠️ 严禁存凭据/env 值（#262 同族，配哨兵）
    source       TEXT             -- 'startup' / 'cli:<script>' / 'api'（P2/未来端点用）
);
```

⚠️ **`tenant_slug` 冗余是刻意的**：审计的价值在于**事后**可读；只存 `tenant_id` 的话，租户被删除后
那条记录就变成一个无意义的数字。**审计记录必须自解释。**

### D2 `PlatformAuditAction` Literal —— **只声明本片有生产者的两条**

```python
PlatformAuditAction = Literal[
    "platform.tenant_create",     # 生产者：seed_default_tenant（首启建 tenant#1）
    "platform.tenant_update",     # 生产者：本片新增的 update_tenant choke point（改 db_dir / allowlist / status）
]
```

⚠️ **刻意不声明** `platform.tenant_suspend` / `platform.tenant_delete` —— 它们的生产者是 **P2 的 CLI**，
本片声明了就会「声明而永不 emit」⇒ 前缀守护必红（或被迫写松 = 等于没守护）。
⇒ **P2 加动作时同片加 Literal**（这条纪律写进 §2 红线）。

> **为什么 `tenant_update` 一条而不是 `db_dir_change` / `allowlist_change` 两条**：动作粒度跟着
> **代码 choke point** 走（一个 `update_tenant` 写口 ⇒ 一条 Literal），变更的**字段**放 `detail_json`。
> 分两条 Literal 会让「将来加第三个可变字段」变成又一次 Literal + 守护改动。

### D3 单一写口 `tenant_repo.update_tenant(tenant_id, **fields)` —— 平台元数据变更的 choke point

- 统一做三件事：① 白名单校验可变字段（`status` / `db_dir` / `allowed_http_hosts` / `name`）；
  ② stamp `updated_at`；③ emit `platform.tenant_update`（含**变更前后值**，但 allowlist 只记
  **变了/条目数变化**、不记内容 —— #262 同族）。
- ⚠️ **诚实声明本片的边界**：运维仍可直接 `sqlite3 UPDATE` **绕过本 choke point** ——
  本片审计的是**代码路径**。⇒ P2 的 CLI 落地后，DEPLOY.md 应把运维引导到 CLI，
  并把「直接 UPDATE」标为**应急手段**。**本片不声称「所有平台变更都被审计」。**

### D4 `tenants.updated_at` 列（第二条平台迁移）

`tenants` 现**无** `updated_at` ⇒「谁改了 `db_dir`」无时间线（v0.9.4 登记）。
照 v0.9.7 刚建的 `_run_platform_migrations` 幂等范式加列。
⇒ 顺带**验证那套机制不是一次性的**（第二个用户）。

### D5 `platform_audit_service.log(...)` —— **fail-closed，不吞**

- 走 `get_platform_conn()`（ctx-free）⇒ **不经** `get_conn`（那是租户库，会撞 fail-closed）。
- **写失败不得吞**（v0.9.4 MF3：`audit_service.log` 曾 fail-soft 吞 `TenantContextError`
  ⇒ 安全记录静默丢失）。
- ⚠️ 但**首启路径**（`seed_default_tenant`）的审计写失败若 raise ⇒ **boot 崩**。
  ⇒ **需要一条明确的取舍**：本片主张 **raise**（fail-closed），理由：平台库刚被 `init_platform_db`
  建好、同一个连接工厂，写不进去说明平台库本身有问题 —— 那时**继续启动才是危险的**（会在一个
  半坏的平台库上服务）。⚠️ 此项**请 Stage 2/3 重点攻**（它是本片唯一可能影响可用性的决策）。

### D6 只读消费者 `GET /api/platform/audit`（不破 E2）

- E2 禁的是**写**操作；只读端点不破它（v0.9.5 已有先例 `GET /api/platform/tenants`）。
- **为什么必须有**：v0.9.5 E4 的教训 —— 一个没有消费者的产物是死码。
  一张**只能靠 `sqlite3` 手查**的审计表，在事故现场没人会想起它。
- 走既有 `require_platform_secret()` 依赖 + 显式列投影（**禁 `SELECT *`** —— `_PUBLIC_COLS` 同款理由）。
- 分页：`?limit=&before_id=`（禁无界返回）。

### D7 `platform_audit` 的哨兵（三条）

1. **前缀守护**：每个 `platform.*` Literal 须有 ≥1 emit（照 `test_metric_invariant_guards` 先例）。
2. **凭据不得进 `detail_json`**：AST 哨兵 —— `platform_audit_service` 的调用点 `detail` 不得含
   `allowed_http_hosts` 的**值** / `auth_value` / env 值（#262 同族；**按标识符判定**，R-SENTINEL-AST）。
3. **单一写口**：`platform.db` 的 `tenants` 表**除 `seed_default_tenant` / `update_tenant` 外
   不得有第三处 `UPDATE tenants`**（AST 扫 SQL 字面 —— ⚠️ 这条须写明为什么不能用 AST 标识符级：
   SQL 是字符串字面量，只能文本匹配；R-SENTINEL-AST 要求写明理由，本条即理由）。

### D8 R-10 audit-on-drift 的处置

R-10 自 v0.9.5 起「因无平台审计落点而未解开」。本片给了落点 ⇒ **但不在本片关它** ——
R-10 的内容是「租户漂移时写审计」，而漂移 tripwire（`assert_tenant_context`）在**租户**侧、
写的应是**租户**审计（`audit_service`），不是平台审计。
⇒ 本片只**移除 R-10 的阻塞理由**并在 CLAUDE.md 更新其状态为「落点已具备，待独立评估」。
⚠️ **不要在本片顺手关 R-10** —— 那是另一件事（scope 蔓延）。

## §4 验收

### 4.1 must

1. 首启（fresh platform.db）⇒ `platform_audit` 有一条 `platform.tenant_create`（tenant#1，含 slug 快照）。
2. `update_tenant(2, status="suspended")` ⇒ 一条 `platform.tenant_update`，`detail` 含
   `status: active→suspended`，且 `tenants.updated_at` 被 stamp。
3. `update_tenant(2, allowed_http_hosts="a.com")` ⇒ `detail` **不含** host 字面（只记「变更了该字段」+
   条目数变化）—— **内容级 oracle**：断言一个确实写进去的 host 串不在 `detail_json` 里。
4. **无 tenant ctx 时**平台审计仍可写（走 `get_platform_conn`）—— 与租户审计的对比测。
5. 写失败 ⇒ **raise**（不吞）：monkeypatch `get_platform_conn` 抛 → `update_tenant` 必须抛。
6. `GET /api/platform/audit`：无密钥 503 / 错密钥 401 / 正确 200 + 显式列（**不含** `detail_json` 里的
   任何凭据）+ 分页有界。
7. **哨兵 1**：每个 `platform.*` Literal ≥1 emit（取材=injection：加一条无 emit 的 Literal → 红）。
8. **哨兵 2**：`detail` 不得含凭据标识符（AST；取材=injection）。
9. **哨兵 3**：`UPDATE tenants` 只出现在两处（取材=injection：第三处 → 红）。
10. 第二条平台迁移幂等 + 存量库（无 `updated_at`）升级后有该列（照 v0.9.7 must #14 形状）。
11. 单租户行为 byte-equal：除首启多一条审计外，全量其余不变。

## §7 自检（moderator：还缺什么？）

1. **D5 是本片唯一可能影响可用性的决策**（首启审计写失败 → boot 崩 vs 继续）。已标请 Stage 2/3 重点攻。
2. **本片不声称「所有平台变更都被审计」** —— 运维直接 `sqlite3 UPDATE` 仍绕过（D3 已诚实声明）。
   这不是缺陷而是边界：审计的是代码路径；P2 的 CLI 落地后再把运维引导过去。
3. **R-10 不在本片关**（D8）—— 它是租户侧的事，顺手关会 scope 蔓延。
4. **`detail_json` 的 PII/凭据面**：本片只记平台元数据，理论上无 PII；但 `detail` 是自由 JSON
   ⇒ 必须有哨兵（D7-②），否则将来有人往里塞 allowlist 内容或凭据。
5. **未测绘到的**：`GET /api/platform/audit` 是否需要按租户过滤（`?tenant_id=`）—— 平台面本就跨租户，
   过滤是便利而非隔离 ⇒ 留 Stage 1' 定。
6. **审计表的增长与清理**：租户库审计有 `purge_audit_log.py`；平台审计量级极小（生命周期动作）
   ⇒ 本片**不做**清理，登记 backlog（避免过早工程化）。
