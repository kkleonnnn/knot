## §1 决议（D1–D8）

### D1 新平台表 `platform_audit`（platform.db）

```sql
CREATE TABLE IF NOT EXISTS platform_audit (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    ts           TEXT    NOT NULL DEFAULT (datetime('now','localtime')),
    actor        TEXT,            -- 见下「actor 口径」；平台动作无登录用户 ⇒ 允许 NULL
    action       TEXT    NOT NULL,-- PlatformAuditAction Literal（见 D2）
    tenant_id    INTEGER,         -- 动作的对象租户（NULL = 非租户维动作）
    tenant_slug  TEXT,            -- 冗余存快照：租户被删/改名后审计仍可读
    success      INTEGER NOT NULL DEFAULT 1,
    detail_json  TEXT,            -- JSON；⚠️ 严禁存凭据/env 值（#262 同族，配哨兵）
    source       TEXT             -- 'startup' / 'cli:<script>' / 'api'（P2/未来端点用）
);
```

⚠️ **`tenant_slug` 冗余是刻意的**：审计的价值在于**事后**可读；只存 `tenant_id` 的话，租户被删除后
那条记录就变成一个无意义的数字。**审计记录必须自解释。**

#### ⚠️ `actor` 口径（M2 —— 草案原写 `ops:<whoami>` 是**错的范例**，已删）

**`kubectl exec` 下 `whoami` = 容器用户（通常 `root` 或 app user）** ⇒ 把「谁」记成 `root`
⇒ **本片的价值命题（「谁改了 `db_dir`」）当场落空**。
⇒ **口径**：`'system:boot'`（启动期 seed，无人参与）· `'cli:<显式传入的 actor>'`（P2）· `NULL`（未知）。
⇒ **P2 的 CLI 必须要求显式 `--actor`（不传则拒绝执行）** —— 已登记进 §8 与弧规划的 P2 条目。

#### ⚠️ 为什么平台表用单列 `actor TEXT`，而租户审计是三列（`actor_id/actor_role/actor_name`）

租户审计的 actor 是**登录用户**（有 id、有 role）；平台动作**没有登录用户**（启动期 / 运维 CLI）
⇒ 三列里两列恒 NULL、第三列存一个自由字符串 = 形状不匹配。
**写明理由是为了防将来有人「顺手统一成三列」** —— 那会让 `actor_role` 这类字段在平台表里恒为空而显得像 bug。

### D2 `PlatformAuditAction` Literal —— **只声明本片有生产者的两条**

```python
PlatformAuditAction = Literal[
    "platform.tenant_create",     # 生产者：seed_default_tenant（首启建 tenant#1）
    "platform.tenant_update",     # 生产者：本片新增的 update_tenant choke point（改 db_dir / allowlist / status）
]
```

⚠️ **刻意不声明** `platform.tenant_suspend` / `platform.tenant_delete` —— 它们的生产者是 **P2 的 CLI**，
本片声明了就会「声明而永不 emit」⇒ 前缀守护必红（或被迫写松 = 等于没守护）。
⇒ **P2 加动作时同片加 Literal**（这条纪律写进 §2 红线）。

> **为什么 `tenant_update` 一条而不是 `db_dir_change` / `allowlist_change` 两条**：动作粒度跟着
> **代码 choke point** 走（一个 `update_tenant` 写口 ⇒ 一条 Literal），变更的**字段**放 `detail_json`。
> 分两条 Literal 会让「将来加第三个可变字段」变成又一次 Literal + 守护改动。

### D3 写侧下沉 `repositories/platform_audit_repo.py` + **emit 与动作同事务**（§I + §II）

```python
# knot/repositories/platform_audit_repo.py —— 同层（先例 = audit_repo），只 import repositories 内部
def insert(conn, *, action: str, tenant_id: int | None, tenant_slug: str | None,
           actor: str | None, success: bool = True, detail: dict | None = None,
           source: str | None = None) -> int:
    """写一条平台审计。⚠️ **连接由调用方注入、本函数不 commit** —— 见下「为什么同事务」。"""
```

**单一写口** `tenant_repo.update_tenant(tenant_id, **fields)`：① 白名单校验可变字段
（`status` / `db_dir` / `allowed_http_hosts` / `name`）；② stamp `updated_at`；
③ **在同一个连接、同一个事务里** `platform_audit_repo.insert(conn, ...)`；④ **单次 `commit()`**。
`seed_default_tenant` 同形（`INSERT tenants` + `INSERT platform_audit` → 一次 commit）。

#### ⭐ 为什么同事务 —— 它把 D5 那个两难整个溶解了（守护者 §II）

草案 D5 曾把「首启审计写失败该 raise 还是继续」标为**本片唯一可能影响可用性的决策**，
并主张 raise。守护者指出 raise 的**真实风险比我写的具体**：
`replicas=1` 是 **R10、零强制**（弧规划 §0.2 自己写明）⇒ 多副本 + 共享 PVC 首启时
**并发写同一个 `platform.db`** ⇒ `database is locked` ⇒ 按 D5 raise ⇒ **全副本 boot 崩循环**。
⇒ **D5 把一个未被强制的运维约束变成了可用性单点。**

**而同事务让这个两难不存在**：
- 「审计写失败」**不再是一个独立事件** —— 它与「动作失败」是**同一件事**（同一个事务一起回滚）；
- ⇒ **零新增失败模式**：boot 崩的条件仍旧只是「seed 本身失败」，这个条件本来就存在；
- ⇒ 并且得到一个**比 fail-closed 更强的性质**：**不存在「动作发生了但没记」或「记了但没发生」**。

⇒ **D5 从「一个可用性取舍」降级为「一个实现细节」**（原 D5 已删，本节取代它）。
⚠️ **残留（登记）**：未来若出现**非事务**的 emit 点（如平台写端点），那时才需要谈 raise 策略 ——
届时调用方是人、可重试，与首启路径的处境完全不同。

#### ⚠️ 本片边界（诚实声明，与草案一致）

运维仍可直接 `sqlite3 UPDATE` **绕过本 choke point** —— 本片审计的是**代码路径**。
⇒ P2 的 CLI 落地后，DEPLOY.md 应把运维引导到 CLI，并把「直接 UPDATE」标为**应急手段**。
**本片不声称「所有平台变更都被审计」。**

### D4 `tenants.updated_at` 列（第二条平台迁移）

照 v0.9.7 刚建的 `_run_platform_migrations` 幂等范式加列。
⇒ 顺带**验证那套机制不是一次性的**（第二个用户）。

原 D5 主张的 raise 会把「`replicas=1` 零强制」这条运维约束变成 boot 可用性单点。

### D6 只读消费者 `GET /api/platform/audit`（不破 E2）

- E2 禁的是**写**操作；只读端点不破它（v0.9.5 已有先例 `GET /api/platform/tenants`）。
- **为什么必须有**：v0.9.5 E4 的教训 —— 一个没有消费者的产物是死码。
  一张**只能靠 `sqlite3` 手查**的审计表，在事故现场没人会想起它。
- 走既有 `require_platform_secret()` 依赖 + **显式列投影**（**禁 `SELECT *`** —— `_PUBLIC_COLS` 同款理由）。
- 分页：`?limit=&before_id=`（禁无界返回）。
- ⭐ **形状照 v0.9.5 的平台只读端点**：api → `platform_audit_repo`（投影做在 SQL 层）+ response model 在 api
  ⇒ 不建 `platform_audit_service`（§0.7 —— 本版唯一偏离守护者处方之处）。

#### ⭐ M3 裁定：**`detail_json` 在投影里（返回）**

守护者要求二选一并写清。**裁定：返回。** 理由：
- 不返回 ⇒ 端点读不到**最有用的字段**（「`db_dir` 从什么改成了什么」），
  那就退化成 v0.9.5 E4 警告过的**死码型产物**（有端点但事故现场没人用）。
- ⇒ **连带后果（必须写在端点处）**：**D7-② 那条「凭据不得进 `detail_json`」的哨兵
  由此成为本端点的承重守护** —— 它不再只是「卫生」，而是「端点不泄漏」的唯一依据。
  端点的 docstring 必须点名它，否则将来有人放松那条哨兵时不会意识到端点也随之破防。

### D7 `platform_audit` 的哨兵（三条）

1. **前缀守护 —— 照 `metric` 先例的「精确集合」形式，不只是「≥1 emit」**（M1）。
   实读 `test_metric_invariant_guards:77`：它断的是 `literals == {"metric.create","metric.update","metric.delete"}`
   **精确相等** + 每条 ≥1 emit。
   ⇒ **精确集合同时封住两个方向**：「声明了但不 emit」**和**「emit 了但没声明」；
   而「≥1 emit」只封前者。
   ⇒ 且它**天然实现 D2 的纪律**：P2 加 `platform.tenant_suspend` 会**打红它**，
   逼「Literal + emit + 守护」三者同片 —— 这正是我们想要的强制。
2. **凭据不得进 `detail_json`**：AST 哨兵 —— `platform_audit_repo.insert` 的**调用点** `detail` 不得含
   `allowed_http_hosts` 的**值** / `auth_value` / env 值（#262 同族；**按标识符判定**，R-SENTINEL-AST）。
3. **单一写口**：`platform.db` 的 `tenants` 表**除 `seed_default_tenant` / `update_tenant` 外
   不得有第三处 `UPDATE tenants`**（AST 扫 SQL 字面 —— ⚠️ 这条须写明为什么不能用 AST 标识符级：
   SQL 是字符串字面量，只能文本匹配；R-SENTINEL-AST 要求写明理由，本条即理由）。

#### ⭐ D7-④ **append-only 哨兵**（Stage 1' 复核新增 · 守护者 §III · 免复核）

全仓 `knot/` 内**不得出现针对 `platform_audit` 的 `UPDATE` / `DELETE`** —— 只允许 `INSERT` + `SELECT`。

**为什么现在就要**（守护者理由，比「卫生」硬）：租户侧审计**已有** `purge_audit_log.py` 这个
**合法 DELETE 先例**，而本片 §7 又把平台审计的清理**登记为 backlog** ⇒ **那个清理脚本一定会来**。
- **有这条哨兵**：它就必须是一次**显式、被评审**的改动。
- **没有**：审计从「**只可追加的证据**」静默变成「**可编辑的记录**」——
  **而这一步不会有任何人注意到**（没有任何测会因此变红）。

⚠️ **判据用文本匹配的理由**（R-SENTINEL-AST 要求写明）：与 D7-③ 同款 ——
SQL 是**字符串字面量**，AST 里看不到「这条 SQL 动的是哪张表」⇒ 标识符级判定原理上答不了这个问题。

4. **无 tenant ctx 时**平台审计仍可写（走 `get_platform_conn`）—— 与租户审计的对比测。

   任何凭据）+ 分页有界。
7. **哨兵 1**：每个 `platform.*` Literal ≥1 emit（取材=injection：加一条无 emit 的 Literal → 红）。
8. **哨兵 2**：`detail` 不得含凭据标识符（AST；取材=injection）。
9. **哨兵 3**：`UPDATE tenants` 只出现在两处（取材=injection：第三处 → 红）。

## §7 自检（moderator：还缺什么？）

1. ~~D5 是本片唯一可能影响可用性的决策~~ → **已溶解**（守护者 §II）：同事务使「审计写失败」与
   「动作失败」成为同一件事 ⇒ **本片不再有影响可用性的决策**。
   ⚠️ 留作教训：我把它标成「最该被攻」是对的，但**我给的解（raise）方向错了** ——
   正确的动作不是在 raise 与吞之间选，而是**让那个两难不存在**。
   而**指出它的正是分层契约**（§I 的重构一并解掉了 §II）—— 分层约束与正确性论证指向同一处。
   **⇒ 判据：当一个决策看起来是「两个都不好的选项」时，先问「这个二选一本身是不是我造出来的」。**
   ⭐ **守护者 Stage 1' §II 背书并再收紧一层（识别信号）**：
   **当两个选项都需要你「定一条策略」（raise 还是吞）时，往往说明那个失败模式本不该存在。**
   **策略题是失败模式的影子；能消掉影子的通常是让本体消失**（此处 = 同事务）。
   ⇒ 并且值得记住是**谁**指出它的：**分层契约**。
   **契约冲突不是绕路的对象，它常常在告诉你结构错了。**
2. **本片不声称「所有平台变更都被审计」** —— 运维直接 `sqlite3 UPDATE` 仍绕过（D3 已诚实声明）。
   这不是缺陷而是边界：审计的是代码路径；P2 的 CLI 落地后再把运维引导过去。
3. **R-10 不在本片关**（D8）—— 它是租户侧的事，顺手关会 scope 蔓延。
4. **`detail_json` 的 PII/凭据面**：本片只记平台元数据，理论上无 PII；但 `detail` 是自由 JSON
   ⇒ 必须有哨兵（D7-②），否则将来有人往里塞 allowlist 内容或凭据。
5. **未测绘到的**：`GET /api/platform/audit` 是否需要按租户过滤（`?tenant_id=`）—— 平台面本就跨租户，
   过滤是便利而非隔离 ⇒ 留 Stage 1' 定。
6. ⚠️ **本版唯一偏离守护者处方的地方是 §0.7（不建 service）** —— 它降低了文件数、
   与 v0.9.5 同一个文件的既有形状一致，但**是我自己的判断，请复核**。
   若守护者坚持建 service，我照办（那只是多一层 passthrough，无正确性差别）。
7. **审计表的增长与清理**：租户库审计有 `purge_audit_log.py`；平台审计量级极小（生命周期动作）

   ⚠️ **但它现在被 D7-④ 挡着** —— 将来做清理必须是一次**显式、被评审**的改动（那正是目的）。
