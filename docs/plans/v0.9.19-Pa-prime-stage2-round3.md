## §B ⭐ 方法论：这一轮的三条，全是**同一条判据的不同变体**

CLAUDE.md 刚折进的那条是「**门校验的 X ≠ 真正被用的 X**」。本轮出现三个新变体：

| 变体 | 实证 |
|---|---|

## §C 阻断项（全部已自核 ✅）

### C1 · ⛔ **§0 那条 fail-open 没有自洽实现**
`is_url_allowed` 的形状是 `return host in get_allowed_hosts()`，而 resolver 返 **`set[str]`**
⇒ **空集 = 全拒**。⇒ 「放行」**无法表达** —— 需要一个「无限制」哨兵 = **第四态**，
而我 §4-13 还写着「三态」。
⇒ **我提请 kk 裁决的那个方案，本身写不出来。**

### C2 · ⛔ **C0''：观测口在机制层不成立**（既有活缺陷）
**我的实测**（`KNOT_LOG_FORMAT=json`）：
```
loguru → {"time":…,"level":"WARNING","msg":"LOGURU-SHAPE",…}
stdlib → STDLIB-SHAPE
```
`logging_setup.py` 里 `InterceptHandler`/`basicConfig`/`dictConfig` **命中 0 次**。
⇒ v0.9.7 的 http allowlist WARN（stdlib）**不是 JSON、无 `level`** ⇒ Kibana 不会把它当 WARNING。
⚠️ 而 `DEPLOY.md:523` 记录排练用 `grep -i warn` 认定「它真的响了」——
**那条消息原文里没有 "warn" 字样**，`lastResort` 又不加 level 前缀 ⇒ **该验证复现不出来**。
⚠️⚠️ **我 v0.9.18 写的 webhook WARN 用 loguru，是好的** ——
⇒ **两条「同形」的 WARN 其实不同形，而我当时默认了它们一样。**

### C3 · ⛔ **C0''：容器内无 `sqlite3`**（既有活缺陷）
**我的实测**：`docker run --rm python:3.11-slim which sqlite3` → **NO sqlite3 CLI**（Dockerfile 无 `apt-get`）。
⇒ DEPLOY 里**所有** `sqlite3 …` 指令在容器内跑不了 —— 含 v0.9.7 的 allowlist 配置、
`quote()` 三态复核、v0.9.15 的应急杠杆。
⚠️ 且 `_PUBLIC_COLS` **不含** `allowed_*` ⇒ **镜像内今天零只读复核路径**
⇒ 运维**无法确认自己配了什么**，也**分不清 `NULL` 与 `''`**（而两者语义相反）。

### C4 · ⛔ D4 只解了 15 red 里的 3 条
共享表 `:72` 那行硬编 `(owner=True, raw=None) ⇒ "env-fallback"`，`:98` 还 `setenv(mod.ENV_NAME…)`
⇒ **加 resolver 也好不了**。出路仍只有两条：造 env（M6 刚否掉）或**开列级例外**（D4 声称避免的）。

## §F 停片建议 + 一条**materially 更简单**的替代

### 先做（都是既有活缺陷，与 SQL allowlist 正交）
1. **C0''**：`logging_setup` 加 `InterceptHandler` 把 stdlib logging 接进 loguru
   ⇒ 修好**所有**用 stdlib 的模块（不止 allowlist），且**订正 DEPLOY:523 那条不成立的验证记录**。
2. **C0'''**：容器内无 `sqlite3` ⇒ 要么 Dockerfile 装它，要么**把 DEPLOY 的运维指令改成不依赖它的形态**
   （例如 `python -m knot.scripts.<只读检查>`），并给 `allowed_*` 一条**只读复核路径**。

### 然后重新审视 P-a' 的范围 —— ⭐ 一个前三版都没认真评估的选项

> **门只装在写路径（POST/PUT），且 `NULL` = 拒绝新建；已存数据源一律不动。**

| | |
|---|---|
| **升级当天** | **零断网** —— 已存数据源**不被重新校验**，照常连 |
| **fail-open** | **没有** —— NULL 时新建被拒（fail-closed），语义干净 |
| **grandfather** | **不需要** —— 不 seed、不 CLI、不迁移、不 fail-open 窗口 |
| **代价** | 升级后到运维配名单之间，**租户加不了新数据源**（功能暂停，**不是**故障） |
| **诚实边界** | **不追溯保护已存行** —— 它止血，不清创 |

⚠️ 第二轮 lens C 否过这个方向，理由是「`create_engine` 看不见新旧 ⇒ 两道门塌回一道」。
**但那个理由假设我们需要纵深门** —— 而若写路径是唯一入口，「先存进去再让它被调用」**根本不成立**
（存不进去）。⇒ 该否决理由**不成立**，值得重新评估。

⇒ **它把本片从「四个子系统」缩回「一个 400 判断 + 一列 + 一份 DEPLOY 说明」。**
剩下的（纵深门 / grandfather / 撤销生效 / 缓存绕过）**各自登记为独立片**，按需再做。
