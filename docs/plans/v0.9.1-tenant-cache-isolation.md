## §3 红线 + 关键设计
- **⭐ R-v091-G2 非对称铁律（守护者最隐蔽正确性点）**：`invalidate_all` 语义相反，**严禁套同一 tid 化模板**——
  - engine `invalidate_all_engine_cache()`（删源撤权）→ **收成当前租户作用域**（删 A 的源不 nuke B 的缓存；承 v0.8.24 stale-schema 修）。
  - token `invalidate_all_token_version_cache()`（rollout 全员 bump）→ **保持真全局 `.clear()`**（收成 tenant-scoped 会留别租户 stale token_version = 安全洞）。
- **MF3 engine 失效器三拆**（删草案「invalidate(uid) 补删 source 键」——**方向错**：source engine 用**源自身**凭据、不从属 user，改密不该 nuke source 引擎）：
  - `invalidate_user_engine_cache(uid)`：仅当前租户 `(tid,uid,…)` 用户键。wire `users.py:85`（改密/改用户）。
  - `invalidate_tenant_engine_cache()`：当前租户全 user+source 键。wire `datasources.py:201`（删源）。
  - 旧 `invalidate_all_engine_cache()` 无它用 → 由 tenant 版替代（名字交 Stage 3 定；留则须真全局或删）。
- **MF4 单一 choke point**：`_tenant_cache_key(*parts)` = `(current_tenant()["id"], *parts)`，engine 4 键 + datasources + rate-limit 全走它（防四处分散手改漏一处 = 仍泄漏）。
- **MF6 R-v091-1 修口（原 byte-equal 与新 fail-closed 自相矛盾）**：改「**有效 tenant#1 请求上下文内**，返回值 + 副作用 byte-equal」（tid=1 常量前缀 → 行为不变）；**无-ctx 调用者转 `TenantContextError` 列为有意契约变化**，须**穷举生产调用者**确认无 startup/health/import 期 ctx-free 命中（当前审计：serving 路径在 cache 行前已 get_conn → ctx 保证）。
- **R-AS-2 身份**（MF5）：`_DS_STATS_CACHE` 保持 re-export 同对象 → 形状 `{tid: {"data","ts"}}`，键在对象内，绝不 rebind。
- **抗诱惑**：不碰 uploads/catalog/auth-split（各自 PATCH）；无新 env / 无 schema 改 / 无新 npm 依赖；契约（get_conn/repo/缓存函数公开签名）除 §3 明列的失效器重命名外 byte-equal。
