## §B ⭐ 最值钱的一条：**我在写下那条规则的同一份文档里违反了它**

Stage 1 §1 我总结了三种伪装，第三种是「**压根不在的**」。
而我 §2 的「已验前提」写的是：
> `main.py` / `repositories/` / `scripts/` **0 处**调 `create_engine` ⇒ 没有无租户 ctx 的路径会撞门。

**lens A 的原话**：
> 「**扫的是文件位置，不是执行上下文。** 唯一无 ctx 的路径恰在 `api/`，
> 被这条判据**结构上排除** —— 正是本片 §1 自己总结的『压根不在的』第三种伪装。」

⇒ **「无租户 ctx」不是一个文件属性，是一个执行属性。** 我按目录扫，
所以那条**在 `api/` 里、由线程池制造的**无 ctx 路径，我的扫描面**看不见它**。

⇒ **判据升级**（建议折进 CLAUDE.md，作为第三种伪装的具体形态）：
> 问「有没有无 ctx 的路径」时，**扫的必须是「谁跨了执行边界」**（`run_in_executor` /
> `to_thread` / `create_task` / 线程 / 子进程），**不是「哪些目录里有调用」**。
> contextvar **不跨线程自动传播** ⇒ 每一处跨边界都是一个候选的无 ctx 路径。

## §C 阻断项（全部已自核 ✅）

### C0 · ⛔ **既有活缺陷（不是本片引入）**：数据源健康探测在**无 ctx 线程**里跑
**证据（我逐行复核）**：`api/admin/datasources.py:137-139`
```python
with ThreadPoolExecutor() as pool:
    statuses = await asyncio.gather(*[loop.run_in_executor(pool, _test_source, s) for s in sources])
```
**没有 `copy_context()`** —— 而本仓其余**三处** `run_in_executor` 全都有，且都带
v0.9.0 C2 的显式注释（`bi_share.py:72` · `bi_reports.py:265` · `bi_schedule.py:68`）。

⇒ 线程内 `current_tenant()` **raise**。后果**今天就在发生**：
`_test_source` 里 `datasources.py:67` 的 `is_url_allowed`（v0.9.7 起 per-tenant）在该线程内抛
⇒ 被 `:86-87` 的 `except Exception: return "error"` 吞
⇒ **所有 HTTP 数据源在 admin 列表里恒显示 "error"，HTTP 200，无日志**。

**为什么没测抓到**：`tests/integration/test_v0821_admin_fetch.py` 的每个 `/status` 测都
`monkeypatch.setattr(ds, "_test_source", …)` **把真函数换掉** ⇒ 真实 `_test_source` 体**零覆盖**
（lens A 实测，与 §3-8 预警的方向相反 —— 我担心的是「全绿」，实际是「压根没跑」）。

⚠️ **对本片的影响是决定性的**：门装进 `create_engine` 后，SQL 源会走上同一条路
⇒ **全部恒 "error"**。⇒ **C0 必须先修，否则本片无法验收。**

### C1 · ⛔ 门选址错：**写路径根本不调 `create_engine`**
`POST /api/admin/datasources`（`:150-161`）只调 `_assert_http_base_url_allowed`
（非 http **首行 return**）然后直接 `create_datasource` 存库 —— **从不调 `create_engine`**。
⇒ 只在 `create_engine` 设门 = **保存成功 + 审计记 `datasource.create` + 那个源永远红着**，
而不是「创建时被拒并给出说明」。

⭐ **根因：我把两个不同的能力混成了一个**（而本仓规则要求「门装在能力被行使的那一行」）：
| 能力 | 门 |
|---|---|
| 「**连到** host X」 | `create_engine` ✅ 我做对了 |
| 「**登记一个指向 host X 的数据源**」 | **POST/PUT** ⛔ 我漏了 |
⇒ 两处都要（写路径拒 **400** + `create_engine` 作纵深）。

### C2 · ⛔ **回退目标不存在** ⇒ 升级即全断
前两份 allowlist 能保住现网，是因为它们的 env **真实存在且 DEPLOY 明写**
（`DEPLOY.md:527` 「所以现网能正常跑」；`.env.example:63,65`）。
而 `KNOT_DB_ALLOWED_HOSTS` **全仓 0 命中** ⇒ 本片新造。
⇒ **三态语义逐字同构，但「回退目标的存在性」不同构**（lens B 原话）。
⇒ 升级后起源租户 `NULL → _parse("") → set() → 全拒` ⇒ **部署方自己的全部 SQL 数据源当场打死**。

**两条候选修法（设计分叉，待 kk 裁）**：
- **(a) 迁移期反向 seed**：`SELECT DISTINCT db_host FROM data_sources WHERE db_type!='http'`
  （+ `users.doris_host` + `cfg.DEFAULT_DB_HOST`）写入该列 ⇒ 现网零改动、已存照旧、新增过门。
  ⚠️ 与 v0.9.7 明写的「**不做启动期自动 seed**」有张力 —— 但那条反对的是**从 env seed**
  （env 仍权威 ⇒ 会漂移）；从**存量数据行** seed 是一次性 grandfather，**seed 后列是唯一来源，无可漂对象**。
- **(b) 本列不设 env 回退**：起源租户 `NULL` = **放行 + 启动 WARN**，fail-closed 推到显式配置之后。
  ⚠️ 这是本片唯一一处会写成 fail-open 的地方，需 kk 明确接受。

### C3 · ⛔ 我 §2 的调用点分类是错的
我写「2 现填 + 4 已存」。**实际 1 现填 + 5 已存**：
`datasources.py:81` 我标成「存前探测」，实际在 `_test_source(s)` 内读 **`s["db_host"]`（已存行）**，
唯一调用点是 `:139` 的批量健康探测。
⇒ 连带 **§4-4 的注入（「门只放在 CRUD 那侧」）按字面构造不出来** —— CRUD 侧压根没有门可放。
