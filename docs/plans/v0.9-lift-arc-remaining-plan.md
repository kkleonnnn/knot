## §1 PATCH 切分（5 片 + 1 chore + lift 片）

> 切分原则：① 一片一个内聚关注点；② **依赖在前**；③ 破坏性动作尽量靠后且集中；
> ④ 每片都能独立全绿（不留「红着往下推」的窗口 —— M3 教训）。

| 片 | 版本 | 内容 | 依赖 | 破坏性 |
|---|---|---|---|---|
| **P1** | v0.9.8 | **平台审计 `platform_audit`**（R7） | — | 无（纯加） |
| **P2** | v0.9.9 | **provisioning 片**（R1 + R2 + R3 + R4） | **P1**（若选端点载体） | 无（新约束仅拦新写入 + 存量校验） |
| **P3** | v0.9.10 | **`_get_secret` 硬化 + `_business_rules` 归正**（R9 + R11） | — | 无（R9 已有启动 fail-fast 兜底） |
| **P4** | v0.9.11 | **scheduler/tick 租户域化**（R8） | P2（需知道租户怎么开通） | 运维需换 CronJob 配置 |
| **P5** | v0.9.12 | **`company` 必填 + 清残留 `resolve_single_tenant`**（R5 + R6） | P2 | ⚠️⚠️ **高** —— 所有不带 `?c=` 的旧链接立即失效 |
| **chore** | riding | **`replicas=1` 强制**（R10） | — | 无 |
| **lift** | v0.9.13 | 删 R-T-GATE 唯一调用点（R12） | 全部 | ⚠️ 放开第二租户 |

**为什么 P1（平台审计）排第一**：它是 v0.9.5 **E2 决策的解锁前提** ——
E2「不引入平台写操作」的**理由**就是「平台动作没有审计落点，而『建/停租户』正是最需要审计的动作」。
⇒ provisioning（P2）若要做成**端点**，必须先有 P1。**这是本弧唯一的强依赖。**

**为什么 P5 排最后（lift 之前）**：它的破坏性（旧链接全失效）**只在 lift 时才是必须的**；
提前落地 = 提前承受破坏而无收益。且 DEPLOY.md 已写明症状形状
（「所有还在用老链接的用户会同时收到『账号或密码错误』」= 预期的 fail-closed，非数据风险）。

## §2 ⚠️ 必须资深架构师先定的 5 个决策点

> 这几条不是实现细节 —— **不同答案会导致不同的 PATCH 切分与不同的红线**。

### D-A（**最关键 · 卡 P2**）provisioning 的载体：CLI 脚本 vs 平台写端点

| 选项 | 代价 | 收益 |
|---|---|---|
| **(a) CLI 脚本**（`knot/scripts/provision_tenant.py`） | 运维必须能进容器/有 DB 访问；无 UI | **不破 v0.9.5 E2**（零平台写操作）⇒ P1 可与 P2 解耦、甚至可延后 |
| **(b) 平台写端点**（`POST /api/platform/tenants`） | **破 E2** ⇒ **P1 必须先做**；且要设计平台侧鉴权的写权限（当前只有共享密钥 + 只读端点） | 可脚本化/可 UI 化；审计天然有 request 上下文 |

⚠️ 与 R4 耦合：无论选哪个，开通动作都必须**强制同时配 `allowed_http_hosts`**（M5 阻断项）。

### D-B（卡 P1）`platform_audit` 记什么

候选动作面（实读 `tenant_repo` 的写口）：`seed_default_tenant` · 开通 · 停用/启用 · 改 `db_dir` ·
改 `allowed_http_hosts` · **登录失败的「代号不存在 / 租户停用」**（v0.9.4 登记：现仅 INFO 日志，
无租户库可写 ⇒ 正是 platform_audit 的用例）。
⚠️ 另需定：`tenants` 是否补 `updated_at`（现无 ⇒ 「谁改了 db_dir」无时间线）。

### D-C（卡 P5）`company` 必填是否与 lift 同片

- **同片**：破坏性集中在一次运维窗口；但那一片会很大（改前端链接分发 + 后端必填 + 清 5 处回退 + lift）。
- **分片**（本文档默认）：P5 先落、lift 后落；代价是 P5 落地当天旧链接就失效（而第二租户还没开）
  ⇒ **承受破坏但无收益**。
⇒ 我的建议：**分片但连续发**（P5 与 lift 在同一个运维窗口内先后合并），兼得两者。

### D-D（卡 P4）scheduler tick 的租户模型

- **(a) per-tenant token**：CronJob 每租户一条（配置量随租户数线性增长）。
- **(b) 单 token + tick 遍历所有 active 租户**：一个密钥仍能 fan-out 全部 ⇒ 需接受「调度是平台级操作」。
- **(c) 单 token + tick 带 `?tenant=<slug>`**：CronJob 每租户一条但共享密钥（折中）。

### D-E（卡 chore）`replicas=1` 是否值得强制

今天是文档一句话。可能的强制：K8s downward API 注入副本数 → 启动期检测 → 多租户 + 多副本时
fail-fast 或 WARN。**不做 = 永远只是一句话**（而这类文档约束在本仓已被证明会漂）。

## §3 每片的红线预登记（各自 Stage 1' 展开）

- **P1**：平台审计**不得**经 `get_conn`（那是租户库）⇒ 必须走 `get_platform_conn`（ctx-free）。
  审计写失败**不得**吞（v0.9.4 MF3 教训：`audit_service.log` 曾 fail-soft 吞 `TenantContextError`）。
- **P2**：新约束**必须同时校验存量**（否则「新写入受约束、存量违规」= 两套现实）；
  `db_dir` 格式校验须与 `tenancy_migration` 既有含容守卫**同源**（禁两份判据）。
- **P3**：R9 删回退后**必须**保留启动期 fail-fast 的友好提示（否则运维只看到 KeyError）；
  R11 归正后 agent 的 `business_rules` 必须与 `query_helper` **同源**，且配一条「两处读同一个值」的测。
- **P4**：tick 不得因某租户失败而中断其余租户（fan-out 需逐租户隔离 + 逐租户日志）。
- **P5**：删回退前**必须**先确认前端所有入口都带 `?c=`（含 SPA 深链、邮件里的旧链接不可控 ⇒ 需一条
  「无代号时给可操作提示」而非裸 401 的产品决策 —— 与 kk 决策②「四类同一句」冲突，**需再裁**）。
- **lift**：删调用点的同片必须删/改 `test_rtgate_still_locks_second_tenant`（它的消息现在会打印完整剩余清单
  ⇒ 是「还差什么」的活文档）。

## §4 我对执行顺序的建议（供拍板）

```
P1 平台审计（无依赖、纯加、解锁 E2）
  → P2 provisioning（R1-R4；载体待 D-A）
  → P3 密钥硬化 + business_rules 归正（可与 P2 并行，无依赖）
  → P4 scheduler 域化（待 D-D）
  → chore replicas 强制（待 D-E）
  → P5 company 必填 + 清残留   ┐ 同一运维窗口
  → lift                        ┘
```

**先做 P1 的另一个理由**：它是**唯一一片完全无破坏性、无待决策阻塞**的（D-B 只影响记什么，
不影响能不能开工），所以可以立刻走 Stage 1' → Stage 2/3。其余各片都至少卡一个决策点。

## §5 自检（moderator：还缺什么？）

1. **本文档不含 R4 的实现载体** —— 它取决于 D-A（CLI 还是端点），故留给 P2 的 Stage 1'。
2. **R11 其实不是多租户项**（是多 catalog 正确性）—— 它挂在 R-T-GATE 清单上属**误挂**，
   建议在 P3 落地时**从清单移出**并在 CHANGELOG 说明（清单里混入非 blocker 会稀释「还差什么」的信号）。
3. **R9 的定性我调过一次**：CLAUDE.md 原写「回退公开默认值」，但**启动期有 fail-fast** ⇒ 活窗口窄
   ⇒ 它是**该修但不紧急**的一项，不该与 R5/R6 那种「lift 即 fail-open」同级。本文档已按此排序。
4. **未测绘到的**：前端有多少处生成登录链接（P5 的真实工作量）—— 需一次前端测绘，留给 P5 的 Stage 1'。
5. **升级排练**（v0.6.1.4 → v0.9.x）与本弧**正交**且是当前最大未验证风险；本文档不含它，
   但建议**不要等 lift 完再做** —— 现网每多停留一个版本，那次跨版升级的风险面就更大。
